# High-Level Design: DragonMIDI

## Problem

Dragonframe (stop-motion capture software) accepts live axis input over OSC, but a MIDI control surface like the KORG nanoKONTROL Studio has no direct way to speak OSC. A prior prototype proved the bridge is possible and captured real protocol knowledge — the nanoKONTROL Studio's Native Mode SysEx handshake, Dragonframe's OSC address space — but its architecture grew unconstrained and isn't a foundation worth building on directly.

Dragonframe's OSC surface includes direct axis-name addressing (`gotoPosition`/`stepPosition`), but DragonMIDI's current mapping only reaches axes indirectly through numbered "OSC encoder channels," which the user must separately wire to an axis inside Dragonframe. A virtual-gamepad approach to real-time jogging is blocked by Apple's DriverKit entitlement requirement. The chosen path instead extends the OSC connection already built: discover axis names via `getAllPosition` and address them directly.

Some Dragonframe functions have no OSC equivalent: the Arc Motion Control workspace's frame stepping ("Step Moco Forward"/"Step Moco Back" in Dragonframe's Hot Keys preferences) is reachable only by its keyboard shortcut. For these, DragonMIDI adds a second, narrower output path alongside OSC: synthesizing the OS-level keystroke that Dragonframe's Hot Keys preferences bind that action to.

A third gap exists: Dragonframe, at startup, opens an outbound WebSocket connection accepting `{"input": "<name>"}` JSON commands; unlike keystroke synthesis, delivery does not depend on Dragonframe holding OS focus. The channel exposes `E-Stop` (motion-control emergency stop), `select-AXn` (axis select/highlight), and `jog-AXn` (per-axis incremental jog) — none reachable by OSC or a safe keystroke. Axis mute/enable-disable and keyframe-setting are not exposed on this channel. For the confirmed subset, DragonMIDI adds a third, narrower output path alongside OSC and keystroke synthesis: a WebSocket server that accepts Dragonframe's connection and forwards mapped controls as Dragonframe WebSocket commands.

DragonMIDI is a clean rebuild: a MIDI-to-OSC bridge for the nanoKONTROL Studio and Dragonframe, with a status UI that shows whether the bridge is alive in both directions, and a mapping view for choosing and confirming what each physical control does.

A second controller, the KORG nanoKONTROL2, is also in scope. It shares the Studio's 8-channel-strip layout (fader/knob/solo/mute) but has no jog wheel, no Scene button, and no Native-Mode-style SysEx handshake — it ships in a fixed-CC "CC mode" selected by a physical button-hold-at-power-on procedure, not something DragonMIDI can request over the wire, and its default CC assignments and MIDI channel differ from the Studio's. Supporting it means the MIDI input and mapping layers can no longer hardcode Studio-only assumptions (a handshake exists, a jog wheel and Scene button exist, channel 16 is the match channel).

DragonMIDI is expected to keep gaining supported controllers over time, contributed by users rather than authored centrally. Turning each new controller into a code change — a new Python `ControllerProfile` instance touching `mapping.py` and `app.py`, per the original two-profile design — doesn't scale past a small, maintainer-authored set. Controller Profiles are instead externalized into standalone config files that a contributor can add without modifying app code, with the app discovering whatever profiles are present at startup.

A third kind of controller breaks the Controller Profile model entirely: Intech Studio's Grid is a modular hardware system where small single-purpose modules (a 4-fader/4-potmeter/4-button module called PBF4, a jog-wheel-plus-buttons module called VSN1) snap together edge-to-edge in whatever physical order and orientation the user chooses, and the assembled chain enumerates as one MIDI device. Grid's own default behavior ("MIDI Auto") assigns each element's MIDI channel/CC/note number from a formula keyed to that module's position in the chain and the element's own index within its module — rearranging which module plugs into the USB host port, or where a module sits in the chain, changes every downstream module's raw MIDI addresses even though the physical controls themselves haven't changed. A Controller Profile's `match_substring` plus fixed per-control CC table, built for a controller whose physical layout is permanent (a nanoKONTROL doesn't get rearranged), has no way to express "whichever fader is physically third from the left, regardless of which raw CC that happens to be today." DragonMIDI instead treats the whole connected Grid as a single controller and derives its logical controls — stable identities like "Grid Fader 3" or "VSN1 Jog" — from a separate topology read (module hardware type and X/Y position, obtained over Grid's own USB-serial control channel, independent of the MIDI connection) rather than from a static per-device CC table. The first phase supports only two module types (PBF4, VSN1) in a single horizontal row; see Delivery Phasing and the Intech Grid path, under System Design, for the full scope and why this stays a separate path alongside Controller Profiles rather than a generalization of them.

Grid's own heartbeat protocol, read directly rather than through Grid Editor, carries no per-module serial number or other persistent identifier — a module's identity within one connected session is its `(x, y)` position after the chain settles, nothing more (confirmed by direct inspection of the heartbeat payload; see `docs/llds/intech-grid.md § Runtime Topology Model`). That is enough to build one working `GridRuntimeController` for whatever is connected right now, but it is not enough to tell two different physical rigs apart: every PBF4+VSN1+PBF4 chain, whether it is the six-actuator Stewart-platform rig built for one shoot or an unrelated four-channel slider rig assembled for another, settles to the exact same module-type shape and was, until this gap was closed, saved under the one constant name `"Intech Grid"` — a second rig silently overwriting the first's saved (Bank, Group) axis table the moment it was connected, with no warning that anything happened. DragonMIDI needs a way for a user to name a specific physical arrangement once ("Stewart Platform Controller") and have that name, not the bare module-type shape, be what the Preset Store keys mappings against — while still refusing to guess which of several identically-shaped saved arrangements a freshly-connected, shape-ambiguous chain actually is.

A rig can have more independently-addressable axes than a control surface has physical faders. Rather than changing what MIDI a fader sends, DragonMIDI adds a switchable **Group** dimension on top of the controller's existing Banks: each Bank's axis assignment becomes one of up to 5 per-Group values instead of a single fixed one, and Track ◄/► steps which Group is active. This reaches up to `5 × bank_count` axes with the same physical faders, without touching the MIDI input or OSC output pipeline — `5 × 8 = 40` for both currently-supported Korg controllers, where `bank_count` (a profile's number of logical channel strips, generalized so it is not a DragonMIDI-wide constant — see Key Design Decisions) happens to be 8.

## Approach

A single desktop app with one continuously-running pipeline:

1. **MIDI in** — connect to the selected controller, picked from a Controller Profile dropdown populated by discovering Controller Profile config files rather than a fixed in-code list (see Controller Profile Loading, under System Design), requesting KORG Native Mode only when the selected profile defines one (the Studio's fixed-CC handshake; the nanoKONTROL2 has none) so every physical control reports a fixed MIDI message.
2. **Mapping engine** — an editable table (add/edit/remove entries, enable/disable per control, MIDI-learn, save/load presets) turns each incoming MIDI event into a Dragonframe OSC message. Each entry has exactly one target, chosen per control: an OSC action, an OSC encoder channel, a direct OSC axis (by discovered name, with user-specified min/max scaling), or an arbitrary custom OSC path. Ships pre-loaded with the nanoKONTROL Studio's default map (mirroring the prior prototype's validated default, see References) as its built-in starting preset. Each Bank's direct-axis assignment is further scoped by the active Group (see Group Switching, under Delivery Phasing) — Track ◄/► changes which of up to 5 per-Group axis assignments a Bank's fader currently addresses, without changing what MIDI the fader itself sends.
3. **OSC out** — send the mapped message to Dragonframe's OSC Input port over UDP.
4. **OSC in** — listen on a local UDP port that Dragonframe's OSC Output preference is pointed at. Any packet's presence is treated as proof Dragonframe is alive and talking back; additionally, responses to a `getAllPosition` query are parsed specifically to discover the current project's axis names, for the mapping view's axis picker.
5. **Keystroke out** — for the small set of Dragonframe functions with no OSC equivalent, synthesize the OS-level keystroke for that function's Dragonframe Hot Key instead. A narrower, secondary output path alongside OSC out, not a replacement for it — most controls never use it.
6. **WebSocket out** — for functions reachable only through Dragonframe's own WebSocket channel (`E-Stop`, axis select, per-axis jog), run a local WebSocket server that Dragonframe connects to at startup, and send it `{"input": "<name>"}` JSON commands. A third, narrower output path alongside OSC out and Keystroke out.
7. **Status UI** — two indicators, "MIDI signal" and "Dragonframe signal," each lit when traffic on that channel has been seen within a short recency window.
8. **Mapping view** — a table of every control's current MIDI source and target, editable in place, including picking a discovered axis name and its scaling range for direct axis targets. Preserved as Table View from Phase 8 onward (see Delivery Phasing), reachable from the Controller view described next.
9. **Controller view** (Phase 8) — the default screen: a per-physical-control list (derived from the active controller via a Control Descriptor, uniform across all four supported controller families) and a contextual Inspector that edits the selected control's existing assignment, dispatched by control type through an Inspector Editor Registry. Edits here and in Table View (item 8) act on the same Mapping Engine state.
10. **Intech Grid** — for Intech Studio Grid controllers (PBF4 + VSN1 modules), a Grid Topology Link opens Grid's USB-serial control channel to read each connected module's hardware type and X/Y position; a Grid Controller combines that topology with PBF4/VSN1 module definitions to normalize incoming raw Grid MIDI — received over the same MIDI backend/normalization as every other controller — into DragonMIDI's logical controls, using Grid's own position-derived default MIDI addressing formula in reverse. Grid-specific behavior ends at that normalization step: once an event resolves to a logical control, it flows through the same Mapping Engine/action/output pipeline a static Controller Profile's logical controls already do, not a separate direct-to-OSC path. Selected from the same Controller Profile dropdown as the nanoKONTROL profiles; its `bank_count` is determined at runtime from whatever modules are connected, rather than declared in a config file ahead of time — see the Intech Grid path, under System Design.

Liveness is recency-based, not connection-based: both indicators answer "was there traffic in the last N seconds," not "is a socket/port open," because UDP has no connection state and MIDI devices can go quiet between moves without being unplugged.

## Target Users

A single-person or small-crew stop-motion animator/DP running Dragonframe on the same or a networked machine, driving axes and transport commands from physical faders instead of a mouse. They need the app's status to be a glance, not a debugging session, and need to be able to confirm and correct a control's assignment without reading source code.

A secondary audience: contributors adding support for a new control surface by authoring a Controller Profile config file. They may know their controller's MIDI layout but not otherwise read or modify DragonMIDI's source, so the config format and its documentation are aimed at them directly, not just at maintainers.

## Goals

- Plug in a nanoKONTROL Studio, launch DragonMIDI, open Dragonframe: both status indicators go live within seconds, no manual configuration required.
- Selecting a controller from the Controller Profile dropdown (nanoKONTROL Studio or nanoKONTROL2) and plugging in the matching device brings both status indicators live within seconds — the same zero-extra-configuration experience, once the profile is chosen.
- Connecting an Intech Studio Grid chain of PBF4 and VSN1 modules (in a single row, any physical order or USB-root choice) and selecting Intech Grid from the Controller Profile dropdown exposes a stable set of logical controls — Grid Fader 1..N, VSN1 Jog, VSN1 Button 1..12 — that don't change identity when the chain is rearranged, even though the underlying raw MIDI addresses do.
- Adding support for a new control surface is a config-authoring task, not a code change: dropping a correctly-formed Controller Profile config file into the user-local controllers folder makes that controller selectable from the dropdown on next launch, with no rebuild required to try it.
- A written guide alongside the config schema lets someone who isn't a programmer author a new Controller Profile config file — declaring capability flags and each control's CC/channel — without reading DragonMIDI's source code.
- Every enabled control in the default map produces the exact Dragonframe OSC message documented for it (see References) — faders/knobs as absolute encoders, transport/shoot/mute/black/delete buttons as one-shot commands, mute/solo as encoder resets.
- DragonMIDI can discover the current Dragonframe project's axis names by querying `getAllPosition` and parsing the per-axis responses.
- The mapping view shows every control's current MIDI source and target in one place, confirmable at a glance.
- Any control's target can be changed to any of: an OSC action, an OSC encoder channel, a direct OSC axis (picked from the discovered list, with a user-specified min/max scaling range), or a custom OSC path — one target per control, chosen by the user, not inferred.
- A fader targeting an axis directly sends `gotoPosition` on every distinct value, scaled into that axis's configured range, with no debounce — matching the same "continuous, no debounce" handling already used for encoder targets.
- MIDI-learn captures a different physical control's exact MIDI source for a mapping entry.
- Mapping changes persist across restarts.
- "MIDI signal" reflects real, recent MIDI traffic from the nanoKONTROL Studio, not just "port opened."
- "Dragonframe signal" reflects real, recent OSC traffic received *from* Dragonframe, not just "we sent something and didn't error."
- Single small desktop build for macOS and Windows, launched like a normal app.
- A control whose only Dragonframe equivalent is a keyboard-only action (no OSC message) can still be mapped, by synthesizing that action's default Dragonframe Hot Key as an OS-level keystroke.
- A control can be mapped to send a Dragonframe WebSocket command (`E-Stop`, axis select, per-axis jog) for functions reachable by no other means.
- Selecting a physical control in the Controller view's list opens its current assignment in a contextual Inspector, for any of the four supported controller families (nanoKONTROL Studio, nanoKONTROL2, PBF4, VSN1), without first finding that control in a dense table.
- Table View remains available as a full-table overview, and an edit made in either the Controller view's Inspector or Table View is immediately reflected in the other — never two mapping states to reconcile.
- Connecting an Intech Grid chain whose module-type shape (recognized module types, left-to-right) has been seen before brings up the same Named Controller and its saved mapping automatically; a shape seen for the first time gets a sensible default name immediately, with no blocking dialog, renamable later — plugging in Grid hardware stays zero-configuration the same way a Korg controller already is.
- Two or more previously-named configurations that happen to share the same module-type shape are never silently chosen between — the user is asked which one applies before any saved axis mapping is activated.
- A chain with more than one VSN1 module (e.g. `PBF4 | VSN1 | PBF4 | VSN1`) builds a working Grid controller, with every VSN1's buttons/jog correctly, globally numbered left-to-right across all VSN1 modules present — the same numbering scheme already used for PBF4's faders/pots/buttons across multiple PBF4 modules.
- The Controller view's control list reflects individual Intech Grid modules for a multi-module chain — which physical module, and its type, each channel and control belongs to — not only a flat Bank/Channel numbering that already crosses module boundaries invisibly.
- Korg nanoKONTROL2/Studio identification stays reliable without a new USB-level dependency: MIDI port-name matching remains the mechanism (confirmed, by this phase's investigation, that neither `mido` nor `python-rtmidi` expose USB VID/PID for a MIDI endpoint on macOS or Windows without new platform-specific code).

## Non-Goals

- Interpreting Dragonframe's OSC output beyond liveness and `getAllPosition` responses — other output (motor-position streaming, custom output-event templates) isn't parsed.
- A general MIDI device picker: within a selected Controller Profile, auto-connect stays scoped to that profile's name match — no picking among arbitrary/multiple MIDI ports, regardless of how many Controller Profile config files exist. The dropdown lists whatever profiles are discovered; it is not a free-text or by-port device browser, and MIDI-learn operates on whatever device the currently selected profile is connected to.
- Dragonframe→controller feedback (LEDs, motorized faders).
- Multi-instance support — running more than one simultaneously-connected controller/session. Group switching (see Delivery Phasing) reaches more axes with one connected controller's own `bank_count` faders (8 for both Korg controllers; whatever a connected Grid chain's normalized fader count is); it is not multi-instance support.
- More than 5 Groups (`5 × bank_count` axes total — 40 for both Korg controllers). Capped at 5 for now, matching the practical ceiling of a rig's physical axis count rather than a protocol limit; revisit if a project needs more.
- Changing what the Scene button does. Group switching uses Track ◄/►, present on both bundled Controller Profiles; the Scene button (Studio-only) still maps to Black, unrelated to Groups.
- Making Cycle (`select-AXn`, cycling across the full discovered axis count) Group-aware. Cycle already operates independently of Bank/Group state and continues to do so.
- Discovering an axis's practical min/max range automatically — Dragonframe has no `getLimits` over OSC, only `setLimits`. The scaling range for a direct-axis target is entered by the user, not read from Dragonframe.
- A general keystroke-automation or macro tool. Keystroke out is scoped to synthesizing the *default* Dragonframe Hot Key binding for specific, documented OSC-gap functions — not arbitrary key combinations, not other applications, and not tracking whether the user has since remapped that Hot Key in Dragonframe's own preferences (same "documented setup precondition, not detected" treatment as the axis `Function: Manual` requirement).
- Detecting or requiring that Dragonframe is the OS-focused application before sending a synthesized keystroke. Like a real keypress, the keystroke lands wherever the OS has focus; DragonMIDI doesn't verify that's Dragonframe first. Accepted as a narrow, self-evident risk for this single-purpose app rather than adding frontmost-window-detection machinery.
- A general third-party control-surface protocol client. DragonMIDI's WebSocket server accepts only Dragonframe's own connection on the well-known port and sends only a fixed set of input names — no dynamic input discovery, coloring, or profile system.
- Coexisting with another process already bound to the same well-known port (59177): not detected, not negotiated around.
- Axis mute/enable-disable or keyframe-setting via the WebSocket path — no command exists for either; unreachable by any output path DragonMIDI has.
- Arbitrary 2-D Grid layouts. Intech Grid support assumes a single horizontal row of modules; if any connected module (recognized type or not) reports a different row, the entire topology is rejected as unsupported and no Grid controller becomes active — not a partial interpretation of whichever subset happens to share one row (`docs/llds/intech-grid.md § Runtime Topology Model`).
- Custom Grid pages, in the sense of user-authored per-page mapping behavior or mid-session page switching. DragonMIDI reads whichever page is actually active from Grid's own protocol data and uses it correctly (not a hardcoded assumption of page 0, `docs/llds/intech-grid.md § MIDI → Module/Element Resolution`) — but a page change *while already connected* is treated as a structural topology change (the Grid controller goes stale and stops resolving events until reselected, below), not interpreted live, and there is no support for distinct per-page mapping configurations.
- User-edited Grid MIDI Auto mappings or Grid Editor Packages. DragonMIDI assumes every module still has its factory-default MIDI Auto addressing; a module customized in Grid Editor (a different CC, a loaded Package, a non-default Lua action) will not resolve correctly.
- A WebSocket-based bridge to Grid Editor or browser tooling. Grid's own topology/control access happens only through DragonMIDI's direct serial and MIDI connections.
- LED or display output back to Grid modules (colors, VSN1's LCD content, etc.) — read-only input in both the topology and MIDI directions.
- Writing to a Grid module's configuration (CC assignment, page layout, Lua actions) — topology discovery is read-only.
- Pressure- or velocity-sensitive button behavior. VSN1's and PBF4's buttons report only press/release in this phase; any pressure/velocity data Grid's firmware includes is ignored.
- Every Intech Grid module. Only PBF4 and VSN1 (both LCD-side variants) are recognized; any other module's hardware-type ID is unrecognized and its elements produce no logical controls.
- Operating more than one independent Grid chain at once. Phase 1 supports exactly one active Grid chain; if more than one candidate Grid USB device is detected, DragonMIDI does not guess which to use or merge them into one topology — it surfaces an ambiguous state and neither becomes active until only one remains (`docs/llds/intech-grid.md § Grid CDC Transport`).
- Guaranteed behavior for rearranging or hot-plugging Grid modules while already connected and operating. The topology link continuously watches for a structural change against the topology the active Grid controller was built from; any such change (a module added, removed, reordered, or changing hardware type at an existing position, a USB-root change, or an active-page change) marks the controller stale and stops it from resolving further Grid MIDI immediately — it is never silently incorporated into ongoing operation. Reselecting Intech Grid from the Controller Profile dropdown is the only supported way to rebuild from a fresh topology after a rearrangement (`docs/llds/intech-grid.md § Topology Change Policy`).
- New motion-control behaviors in the controller-oriented UI redesign (Phase 8): center-stop shuttle, absolute-knob jog, relative-jog handling, endpoint teaching, soft-limit management, rig calibration, motor coupling. The Inspector introduced in Phase 8 exposes only the existing axis-target assignment; other control types render with no editable behavior yet, rather than a control that looks configurable but does nothing. These remain later roadmap items (`docs/roadmap.md`).
- A second, independent mapping state introduced by Phase 8. The Controller view and Table View read and write the same Mapping Engine/Preset Store state through one shared query/update surface — see System Design and Key Design Decisions.
- A Preset Store persistence-format change for Phase 8. The (Bank, Group) axis-target JSON schema (`docs/llds/app-ui.md § Preset Store`, `preset_store.py`) is unchanged; the Control Descriptor and Inspector Editor Registry (below) are a presentation-layer addition only.
- New simultaneous-controller behavior introduced by Phase 8. The Controller view still edits one connected controller at a time, same as today's Controller Profile dropdown; see the existing multi-instance Non-Goal above.
- Per-physical-module persistent identity. Grid's heartbeat protocol has no serial number or other identifier that survives a module being unplugged and replugged elsewhere; a Named Controller's saved identity is a module-type shape (the ordered sequence of recognized module types after normalization), never an individual module's history. Swapping two modules of the *same* type within an otherwise-unchanged shape is not detected — this was already an accepted limitation of Bank's positional persistence (`docs/llds/intech-grid.md § Persistence`) and remains one.
- Configuration versioning or history. Save and Save As each write the configuration's complete current state in one atomic rewrite, the same as the Preset Store always has; there is no undo beyond not saving, and no record of a configuration's prior states.
- Copying a saved configuration's mapping onto a different hardware key. A saved configuration's `profile_name`/`module_shape` is fixed at creation (`docs/llds/named-controller.md § 1`, unchanged); Save As creates a sibling under the *same* hardware key, never a different one. Retargeting a mapping to different hardware is not supported.
- Deleting a saved configuration from the UI. Still out of scope, per `docs/llds/named-controller.md § 8` — unaffected by this phase's Save/Save As/Load additions.
- Live hardware-mismatch recovery beyond the existing stale-and-reselect mechanism. A structural topology change mid-session still marks the active Grid controller `STALE` (`docs/llds/intech-grid.md § Topology Change Policy`) exactly as before; Named Controller matching only runs again at the next fresh settle — it does not add a second, independent live-reconciliation path.
- USB VID/PID-based MIDI device identification. Investigated for this phase: neither of DragonMIDI's MIDI libraries exposes USB VID/PID for a MIDI endpoint on macOS or Windows without new, platform-specific code outside the existing dependency set; name-substring matching (already proven reliable for both Korg controllers) remains the sole identification mechanism, matching the same choice already made for Grid's own MIDI port (`docs/llds/intech-grid.md § Controller-Defined bank_count and MIDI-Port Discovery`).

## Delivery Phasing

This HLD describes the target architecture. It is delivered in phases rather than all at once:

- **Phase 1 — Axis discovery, direct axis addressing, and bank derivation.** The OSC Listener gains the ability to parse `getAllPosition` responses into a list of axis names. The mapping view lets the user assign each of the 8 faders to a discovered axis name with a min/max scaling range — this is now the fader's default target, not an opt-in alternative. The Mapping Engine sends `gotoPosition` continuously, scaled into that range, on every distinct fader value. Each fader's channel strip forms a **bank**: once a fader has an axis assigned, its bank's knob automatically sends `stepPosition` (a signed nudge relative to center) and its Mute button automatically sends `setZero` — neither is independently configurable. (Solo originally followed the same pattern with `setHome`; superseded in Phase 3 below, where Solo becomes an unconditional WebSocket target instead.) Record/Select keep their existing (unmapped) target untouched in this phase. The jog wheel drives frame-by-frame timeline stepping (`stepForward`/`stepBackward`, one step per detent, direction from the wheel's rotation) rather than motion-control axis input, and additionally synthesizes the "Step Moco Forward"/"Step Moco Back" keystroke on the same detent so stepping also works while the Arc Motion Control workspace is focused, where the OSC commands alone have no effect; Return to Zero remains unmapped.
- **Phase 2 — The rest of the configuration.** Extend target selection (OSC action/encoder/direct-axis/custom-path) to knobs and buttons; add MIDI-learn, enable/disable, add/remove/duplicate entries, and preset save/load. This is where the mapping view reaches the full editor generality described elsewhere in this document.
- **Phase 3 — WebSocket output.** Add the WebSocket target type (`E-Stop`, axis select, per-axis jog — the confirmed subset) and the WebSocket Output Adapter that serves it. Independent of Phase 2's OSC/Keystroke target work; can land before or after it.
- **Phase 4 — nanoKONTROL2 support.** Introduce the Controller Profile abstraction (`docs/llds/midi-input.md`, `docs/llds/static-mapping.md`), a nanoKONTROL2 profile (no handshake, no jog wheel, no Scene button, its own default channel/CC map), and the Controller Profile dropdown in the Status UI (`docs/llds/app-ui.md`). Independent of Phases 1–3's OSC/Keystroke/WebSocket target work — it changes which device profile feeds the same mapping/output pipeline, not the pipeline itself.
- **Phase 5 — Pluggable Controller Profiles.** Replace the hardcoded `STUDIO_PROFILE`/`NANOKONTROL2_PROFILE` Python instances with standalone config files, one per controller, using a semantic/templated schema: capability flags plus a per-control CC/channel list, with the existing `_fader_entries()`/`_knob_entries()`/etc. helpers synthesizing the opinionated map from that declaration (`docs/llds/static-mapping.md`). A Controller Profile Loader (`docs/llds/midi-input.md`) discovers profiles from two locations — a bundled folder shipped inside the app build, and a user-local folder for testing new profiles without a rebuild — merging them, with the user-local file winning outright on a name collision. The Controller Profile dropdown (`docs/llds/app-ui.md`) populates from whatever the loader discovers, not a fixed tuple. Ships with a companion authoring guide aimed at non-programmer contributors. Independent of Phases 1–3; supersedes Phase 4's mechanism (hardcoded instances), not its two profiles' actual behavior.
- **Phase 6 — Group switching.** Introduces the Group dimension: 5 fixed Groups, each covering 8 axes (Group *g* = axes `8·(g-1)+1` .. `8·g`). Track ◄/► (`previous_track`/`next_track`) steps the Mapping Engine's active-Group index by one instead of their current `stepBackward`/`stepForward` OSC targets — a real behavior change, accepted because Rewind and Previous/Next Marker already cover the same "step back/forward" gesture (`docs/llds/static-mapping.md`'s Transport/marker/track section defaults), so no gesture becomes unreachable. Exact boundary behavior (wrap vs. clamp at Group 1/5) is an LLD-level decision. Each Bank's axis assignment becomes a per-(Bank, Group) lookup instead of a single fixed value — Knob N/Mute N continue deriving from Bank N's fader per the existing Bank Derivation rules (`docs/specs/static-mapping.md`), now reading whichever axis the active Group currently points Bank N at; Solo N's WebSocket target becomes Group-aware, sending `select-AX(N + 8·(g-1))` in place of the fixed `select-AXN` (`MAP-WS-002`). The Mapping View's 8 fader rows each show 5 axis-picker dropdowns (one per Group, leftmost = Group 1) instead of one, plus a new row of 5 indicator lights showing the active Group. This is also the first real implementation of the Preset Store shown in System Design below, scoped narrowly to this (Bank, Group) → axis table — not the general named-preset save/load system that remains Phase 2 scope. The table persists to a new `~/Documents/DragonMIDI/configurations/` folder, sibling to the existing `controllers/` folder; the active Group index itself is not persisted and always starts at Group 1 on launch, matching every other piece of engine state today. Independent of Phases 1–5's device/profile work — it changes how many axes the same 8 fader channel strips can reach, not the underlying MIDI/OSC pipeline.

- **Phase 7 — Intech Grid support (PBF4 + VSN1, linear topology).** Adds the Grid Topology Link (reads module hardware type and X/Y/rotation over Grid's USB-serial control channel), module definitions for PBF4 and VSN1, and a Grid Controller that normalizes a linear (single-row) arrangement's modules into stable logical controls, translating incoming Grid MIDI into them by reproducing Grid's own position-derived default addressing formula. Intech Grid becomes a third Controller Profile dropdown entry whose `bank_count` is derived at runtime from the connected chain (the same controller-defined `bank_count` property every profile already has — see Key Design Decisions — generalized ahead of this phase specifically so Grid could use it without further engine changes) rather than fixed at 8 like the Korg profiles. Grid-specific behavior ends at normalization: a resolved logical control then drives Dragonframe through the same Mapping Engine/Bank/Group/Preset Store/Mapping View pipeline the Korg profiles already use, not a separate direct-to-OSC path — see the Intech Grid path, under System Design, and Key Design Decisions. Independent of Phases 1–6's device/profile work; VSN1's jog wheel and buttons are exposed as logical controls but are not yet wired to a default action beyond what's needed for the stated tests.
- **Phase 8 — Controller-oriented UI redesign (UI and architecture only).** Replaces the Status window / Mapping View / Configuration Dialog trio as the default screen with one **Controller view**: a compact connection header (collapsed MIDI/Dragonframe indicator dots, with host/port editing and per-profile setup guidance relocated to a new, thin **Settings dialog** behind a ⚙ control — a container around the Status window's existing fields, not a new mechanism), the existing Controller Profile dropdown, a horizontal Group selector showing the existing `_GROUP_LETTERS` A–E labels (Phase 6's Group mechanism, now surfaced as the primary layer control rather than a column header inside a table), a scrollable list of the active controller's physical controls, and a contextual **Inspector** panel editing the selected control's existing axis-target assignment. Introduces two new presentation-layer pieces to support this without touching the Mapping Engine's internal representation or the Preset Store's file format: a **Control Descriptor**, unifying each `ControllerProfile`'s static control list and the Grid Controller's runtime-derived logical controls into one list of `(id, label, control_type, bank)` entries the control list and Inspector render identically regardless of controller family; and an **Inspector Editor Registry** keyed by `control_type`, holding today only the axis-target editor (the same assignment the existing `_AxisTargetEditor` already edits) behind a documented extension point for future per-type editors (center-stop shuttle, absolute-knob jog — a later phase, not this one). The prior Mapping View + Configuration Dialog combination is preserved as **Table View**, reachable by a toggle from the Controller view; both views read and write the Mapping Engine through its existing `set_axis_target`/`clear_group_axis_target` methods and `mapping_view_model.py`'s existing pure read functions (`axis_picker_state`/`group_axis_picker_states`) — the same calls Table View's widgets already make — so no second mapping state is introduced (`docs/llds/app-ui.md § Control Descriptor and Inspector Editor Registry`). Independent of Phases 1–7's device/protocol work — it changes how existing assignments are presented and edited, not what MIDI/OSC/Keystroke/WebSocket traffic the app sends.

Everything below describes the full target architecture; phase boundaries are tracked in the LLDs, not restated per-section here.

**Threading model:** MIDI input arrives on a callback thread; the OSC listener runs its own receive loop/thread. Both push into thread-safe queues that the Qt event loop drains on a timer, avoiding Qt widget access from a non-UI thread.

**Controller Profile:** `MIDIIN` and `MAP` are driven by whichever active controller is currently selected — a static `ControllerProfile` for the Korg devices, or the runtime-built `GridRuntimeController` for Intech Grid, both satisfying the same structural `ActiveController` shape (see Key Design Decisions, and `docs/llds/intech-grid.md § Active Grid Controller` for exactly what that shape is) — the diagram's boxes are the same regardless of which controller is active; only their internal behavior (handshake yes/no, opinionated map contents, default channel) varies per profile. Switching the dropdown disconnects the current device (releasing Native Mode first, if the outgoing profile had it) and starts discovery for the newly-selected profile's name pattern.

**Controller Profile Loading:** `ControllerProfile` instances are no longer Python literals; they're parsed from config files discovered at startup from two locations — a bundled folder shipped inside the app build, and a user-local folder read directly off disk (no packaging involved), so someone can test a new profile without a rebuild. Both locations are scanned on every launch and merged into one list keyed by profile name; when a user-local file and a bundled file share a name, the user-local one wins outright (skipped, not field-merged) — see `docs/llds/midi-input.md § Controller Profile Loading`.

**Intech Grid path:** Unlike every other Controller Profile, Intech Grid is not expressed as a `ControlsConfig` YAML file — its control layout isn't known ahead of time, only discovered at runtime. Selecting it from the Controller Profile dropdown instead activates two Grid-specific components: the **Grid Topology Link**, which opens Grid's USB-serial control channel (separate from, and in addition to, the ordinary MIDI connection `MIDIIN` opens) and continuously decodes heartbeat broadcasts into each connected module's hardware type and X/Y position; and the **Grid Controller**, which combines that topology with PBF4/VSN1 module definitions to build the current set of logical controls and to translate each raw MIDI event `MIDIIN` receives (reusing the same backend and `normalize_raw()` every other profile uses — Grid's default behavior produces ordinary CC/Note messages, nothing Grid-specific in the wire format itself) into a `(module, element) -> LogicalControl` resolution, by reproducing Grid's own position-derived default MIDI-addressing formula in reverse. **Grid-specific knowledge ends there.** The resolved logical control is handed to `MAP` exactly as a static Controller Profile's own `(type, number)` keys already are — from that point on, Grid uses the same Mapping Engine, and through it the same Preset Store and Mapping View, that the Korg profiles do, with its `bank_count` (how many logical Fader-role controls the connected chain currently has) supplied by the Grid Controller at runtime instead of read from a config file — see Key Design Decisions.

**Named Controller Registry:** closes the gap the Problem section's Grid-identity paragraph describes — the Preset Store's existing per-profile-name keying is exactly right for a Korg controller, whose physical shape never varies, but wrong for Intech Grid, whose shape is rediscovered fresh every connection and was, until this phase, always folded into the one constant key `"Intech Grid"` regardless of what was actually plugged in. A small new persisted registry (`~/Documents/DragonMIDI/named_controllers/`, one JSON file per entry, mirroring the Controller Profile/Preset Store folders' own one-file-per-name convention) records, for each Named Controller, a stable `id`, a user-editable `display_name`, and either a reference to a static Controller Profile's name (Korg) or a `module_shape` — the ordered sequence of recognized module-type names a settled `GridTopology` normalizes to (`docs/llds/intech-grid.md § Runtime Topology Model`), after excluding unrecognized modules exactly as element enumeration already does. Every Korg profile gets exactly one Named Controller auto-created the first time it's selected, whose `id` is the profile's own name — a transparent wrapper satisfying the Hardware Definition / Named Controller / Mapping Preset distinction in name only, with zero behavior change, since a Korg device's physical shape can't vary and there is nothing to disambiguate. Intech Grid is where this does real work: every time a `GridTopology` settles (§9's Initialization Lifecycle, unchanged), the Grid Controller's resolved `module_shape` is looked up against every stored `kind="grid"` Named Controller. Zero matches (a shape never seen before) auto-creates a new entry with a shape-derived default display name (e.g. `"Intech Grid (PBF4+VSN1+PBF4)"`) and activates it immediately, with no blocking dialog — preserving Grid's existing zero-configuration feel; the name can be edited later. Exactly one match silently activates it, the same zero-friction behavior Korg already has. Two or more matches — only possible once a user has deliberately saved more than one arrangement sharing an identical module-type shape — is the one case that blocks: DragonMIDI cannot tell the ambiguous arrangements apart (see Key Design Decisions' Persistent Module Identity bullet, below), so it asks which saved Named Controller applies before any saved axis mapping takes effect, rather than guessing. The Preset Store's existing `profile_name`-keyed `load_group_axis_targets()`/`save_group_axis_targets()` calls (`docs/llds/intech-grid.md § Persistence`) are unchanged in shape — only the string they're called with changes, from the bare controller-family name to the active Named Controller's `id`. A one-time migration path covers an installation that already has a legacy `Intech Grid.json` preset file predating this phase: the first settle after upgrading, with no Named Controllers yet recorded, creates one whose `id` is the literal string `"Intech Grid"` (reusing the legacy filename outright, zero data loss) bound to whatever shape is connected at that moment — exactly reproducing pre-Phase-1.3 behavior for a user with one rig, and falling through to the ordinary zero/one/many matching logic described above for every connection after that.

**Named Configuration (generalizing the above):** the registry's "exactly one record per hardware key" assumption is lifted — `profile_name`/`module_shape` is a key zero or more saved `NamedController` records can share, each a distinct, independently loadable mapping. The auto-created/migrated record above is flagged `is_builtin=True` and protected from direct overwrite; Save As creates additional, equally-persisted siblings under the same hardware key, discoverable via the registry's existing load-and-filter pattern with no new file format. See Key Design Decisions for the Save/Save As/Load surface this enables and how it keeps Grid's connect-time ambiguity safety unchanged.

**Group state:** the active Group index is a single engine-level value on `MappingEngine`, following the same precedent as `_cycle_index` — one engine instance drives one connected device at a time, and switching the Controller Profile dropdown already clears all per-control engine state outright, so Group index needs no per-profile tracking. Each Bank's per-Group axis assignments are loaded from the Preset Store at startup and written back on every change (matching the mapping view's existing no-separate-save-step pattern), independent of whether a device is currently connected.

Both the Control Descriptor and the Registry read and write the mapping through `MappingEngine`'s existing `set_axis_target`/`clear_group_axis_target` methods and `mapping_view_model.py`'s existing pure read functions — the same calls Table View's widgets already make, not a new API surface — so the two presentation surfaces can never drift into two mapping states.

## Key Design Decisions

- **Python + PySide6.** Domain knowledge (Native Mode SysEx handshake, OSC address space) is already validated against mature Python MIDI/OSC libraries. PySide6 over the prototype's tkinter for a cleaner UI; over native Swift or Electron to keep Windows support without an Electron-scale runtime for an always-on utility.
- **Liveness via recency window, not connection state.** MIDI has no "hello" and Dragonframe's OSC is UDP (connectionless), so "connected" is meaningless for either channel. Native Mode handshake success/failure is a separate, orthogonal signal (surfaced as the *error* state) since a control can be silent yet still alive.
- **Bidirectional OSC instead of a send-side heartbeat.** Dragonframe's documented "Outputting Axis Positions via OSC" feature lets it emit traffic on its own; listening for that is real evidence Dragonframe is alive, versus a send-only heartbeat which only proves the local socket didn't error.
- **Direct axis-name addressing instead of a virtual gamepad.** A virtual gamepad is Dragonframe's only mechanism for true continuous jogging, but both the current (`IOHIDUserDeviceCreateWithProperties`) and legacy (`IOHIDUserDeviceCreate`) macOS APIs require the same Apple-granted DriverKit entitlement, unavailable without an approval process outside this project's control. Extending the already-working OSC path with `gotoPosition`/`stepPosition` avoids introducing a new OS-level dependency; whether the resulting feel is smooth enough remains open, not a blocker to building it.
- **Axis names discovered via `getAllPosition`, not hand-typed.** Dragonframe has no other way to enumerate an axis's name; the OSC Listener parses this one specific response shape into a name list for the mapping view, without becoming a general interpreter of Dragonframe's other OSC output.
- **Per-axis min/max scaling entered by the user, not discovered.** Dragonframe has `setLimits` but no `getLimits` over OSC — an axis's practical range cannot be read back, only set. The mapping view asks the user for it directly.
- **Mapping isolated behind one interface.** The mapping engine (MIDI event in, OSC message out) is a pure, swappable component — the editor, persistence, and MIDI-learn sit on top of it without touching MIDI I/O, OSC I/O, or the status indicators.
- **Mapping editor defaults to the nanoKONTROL Studio's opinionated map** rather than an empty table, so the zero-config experience is unchanged for anyone who never opens the mapping view.
- **Configuration is a separate dialog, not a second embedded section.** Unlike the Mapping View (embedded in the main window since Phase 1), the Configuration dialog holding every non-fader-axis control assignment opens on demand from a button and is closed to return to the main window. The main window's whole purpose — glanceable status plus the fader-axis grid a user adjusts often — would be diluted by permanently showing rows (Play, Stop, Scene, transport, etc.) a user only needs to confirm rarely; a dialog keeps those two concerns visually separate without losing either one's "confirm at a glance" property once opened. Chosen over keeping one combined table (the pre-2026-07-23 design) or an inline expand/collapse panel (user's explicit choice, 2026-07-23).
- **Configuration collapses to one row per control type, not one row per physical instance.** Knob, Mute, and Solo behave identically across all of a profile's channel strips (bank-derived, or a single mechanical formula) — showing one near-identical row per strip would repeat the same fact `bank_count` times for no additional information a user could act on differently per instance, the same reasoning already applied to Solo's pre-existing single summary row. Only the Fader row differs: it hosts the OSC axis ↔ OSC encoder mode switch, which is now a single control governing all of a profile's faders together rather than one independent per-fader flag each (a reversal of the prior per-fader model, user's explicit choice, 2026-07-23) — simpler to reason about and to show in one row, at the cost of no longer being able to mix modes across faders.
- **`bank_count` is a property of the active Controller Profile, not a DragonMIDI-wide constant.** Both bundled Korg profiles resolve to `bank_count = 8`, derived from their declared `faders` list (`ControllerProfile.bank_count`, `docs/llds/static-mapping.md § Controller Profile Config Schema`) rather than an independently-declared count — a config author states a device's fader CCs once, and its strip count follows. Generalized ahead of any controller actually needing a different count, specifically so a topology-derived controller (Intech Grid, below) can have a runtime-determined width without the Mapping Engine's Bank/Group math, the Preset Store's Bank-index bounds, or the Mapping View's row count changing at all — each already reads `bank_count` from the active profile rather than a fixed `8`. `knobs`/`mutes`/`solos` are separately, independently sized — not required to match `faders`' count — so a profile can also declare more encoders than channel strips.
- **One target per mapping entry, not multiple.** A control drives exactly one target — matches "select what I want each control to do" as a single choice, not a dual-purpose one, and keeps the mapping engine's per-entry logic simple.
- **Auto-connect by name within the selected Controller Profile, no general device picker.** Scanning MIDI inputs for a name match removes a manual connect step. If the device isn't found, the MIDI indicator stays quiet and the app keeps retrying.
- **Controller Profile abstraction, not per-device forked code.** `MidiInputAdapter` and the Mapping Engine are driven by a `ControllerProfile` (device name-match pattern, optional Native-Mode-style handshake, default MIDI channel, feature flags, opinionated default map) rather than hardcoding the nanoKONTROL Studio's quirks throughout. The nanoKONTROL Studio and nanoKONTROL2 ship as two Controller Profile config files rather than two profile instances; a third controller is a new config file, not new code. Chosen over forking the adapter/engine per device (more duplicated boilerplate — discovery polling, bank derivation, WebSocket-targeted controls all repeated) or scattering `if profile == "studio"` conditionals through shared code (doesn't scale past two devices). This decision predates Intech Grid, which generalizes it further still: Grid is not a `ControllerProfile` config file at all, but a separate `GridRuntimeController` satisfying the same `ActiveController` shape — see the Grid-specific Key Design Decision bullets below and `docs/llds/intech-grid.md § Active Grid Controller`.
- **Controller Profile config files declare structure, not the derived map.** A config file lists capability flags (`has_jog_wheel`, `has_scene_button`, `default_channel`) and a per-control list mapping physical control names to CC numbers — it does not enumerate the full MIDI-event-to-OSC-message table entry by entry. The existing shared helpers (`_fader_entries()`, `_knob_entries()`, `_mute_entries()`, `_shared_button_entries()`) synthesize the actual opinionated map from that declaration, the same way they already build `OPINIONATED_MAP_STUDIO`/`OPINIONATED_MAP_NANOKONTROL2` internally — so every controller gets identical fader/knob/mute behavior for free, and a config author states facts about their hardware rather than re-deriving OSC actions. Chosen over a fully flat per-key table (simpler schema, but ~50 hand-copied entries per controller with no shared-invariant enforcement) and a YAML-level template/inheritance mechanism (avoids touching Python for template changes, but adds a new merge system for marginal benefit over reusing the helpers directly). Controls whose action differs from what the shared helpers produce (e.g. the Studio's Scene button → black) need an explicit override in the config schema — the exact override shape is an LLD-level decision.
- **Controller Profiles load from two locations, user-local overriding bundled.** A bundled folder ships inside the app build (added to PyInstaller's `datas`, resolved via the existing frozen-vs-dev `sys._MEIPASS` branch already used for icon/image assets) and a user-local folder is read directly from disk (`~/Documents/DragonMIDI/controllers/`) on every launch — no rebuild needed to try a new profile. When a user-local file's name collides with a bundled one, the user-local file wins outright; the bundled entry is skipped, not field-merged, letting someone override or iterate on a shipped profile without touching the repo.
- **Controller selection is an explicit dropdown, not auto-detection.** The user picks a profile from a Status UI dropdown populated by whatever Controller Profile config files are discovered; auto-connect-by-name then applies only within that profile. The dropdown's contents are open-ended (any discovered profile), but it is still not a general device picker — no picking among arbitrary/multiple MIDI ports within a profile — see Non-Goals.
- **nanoKONTROL2's opinionated map omits jog-wheel and Scene-button entries entirely**, rather than including them as disabled/greyed-out placeholders. The nanoKONTROL2 has no jog wheel and no Scene button, so the Studio-only frame-stepping (OSC + Arc keystroke) and Scene→Black mappings simply don't exist as rows in its profile.
- **nanoKONTROL2's default CC map is the commonly-documented factory-default CC-mode assignment, confirmed working against real hardware.** Korg's owner's manual documents the physical layout and operation modes but not the actual CC-number table (a separate Parameter Guide has that, and it likewise doesn't list the factory defaults — see References); the map was written from the widely-cited community-documented values and confirmed in practice against a real nanoKONTROL2 (2026-07-21) — every control produced its expected Dragonframe behavior. This was a practical, in-app confirmation (controls behaving correctly), not a byte-level MIDI-monitor trace of the raw CC numbers.
- **`pynput` for keystroke synthesis, over native platform APIs.** One dependency covers both macOS (via the same Accessibility-permission-gated mechanism as `Quartz`/`CGEvent`) and Windows (via `SendInput` under the hood), matching the existing preference for validated, portable libraries (`mido`+`python-rtmidi` for MIDI) over hand-rolled per-OS code.
- **Keystroke output fails silently, not as a new status indicator.** Unlike the MIDI Native Mode handshake (surfaced as an *error* state) or the OSC listener bind failure, a missing macOS Accessibility grant or a Windows `SendInput` failure is logged but does not add a third Status UI indicator in this phase — the affected controls are few, and the existing two indicators (MIDI signal, Dragonframe signal) already tell the user whether the *OSC* half of the bridge is healthy. A dedicated indicator is deferred, not ruled out, if more controls come to depend on keystroke output later.
- **No frontmost-application check before sending a keystroke.** Synthesizing a keystroke without first verifying Dragonframe is the OS-focused app mirrors how the physical keyboard shortcut itself behaves — it also does nothing useful if focus is elsewhere. Adding detection machinery for a single-purpose app used almost exclusively alongside Dragonframe wasn't judged worth the added platform-specific code (`NSWorkspace` on macOS, `GetForegroundWindow` on Windows).
- **DragonMIDI runs the WebSocket server; Dragonframe is the client.** Dragonframe connects outward to `ws://localhost:59177/com.dzed.dragonframe/DragonframeConnection` at startup. DragonMIDI's WebSocket Output Adapter binds that port and accepts the connection — inverted from OSC out (DragonMIDI-initiated); Dragonframe does not listen on this channel.
- **A fixed, curated list of WebSocket target names, not a free-text field.** Dragonframe recognizes 19 static input names plus the dynamic `select-AXn`/`jog-AXn` pair; only `E-Stop`, `select-AXn`, and `jog-AXn` fill a gap no other output path covers. The mapping editor's WebSocket target picker offers only these, mirroring how OSC action targets are picked from a known list rather than typed freehand.
- **WebSocket output fails silently on bind failure**, matching the Keystroke precedent above — if port 59177 is already held, the adapter logs the failure and WebSocket-mapped controls do not fire; no third status indicator, no retry-with-backoff UI.
- **"Group" is a distinct dimension from "Bank," not a redefinition of it.** Bank N (Fader N + Knob N + Mute N + Solo N) keeps its existing meaning throughout `docs/specs/static-mapping.md` — a fixed, positional channel-strip pairing, still exactly 8, still not itself switchable. Group is new: which axis each Bank currently resolves to. Kept as two separate terms specifically to avoid overloading "Bank," which already has a settled meaning across existing specs.
- **Track ◄/► drives Group switching, not the Scene button.** Track ◄/► is present on both bundled Controller Profiles; the Scene button exists only on the Studio (`has_scene_button`) and is already mapped to Black. Group switching needed one mechanism that works identically on every profile, which ruled out Scene.
- **Fixed at 5 Groups, not sized to the discovered axis count.** The ceiling is a rig's physical axis count, not a protocol limit; 5 covers today's known use and leaves room to raise the constant later without an architecture change, rather than building dynamic sizing for a need that hasn't materialized.
- **Per-(Bank, Group) axis assignments persist; the active Group index does not.** This is the first real Preset Store implementation (the box existed in this diagram since Phase 2 was scoped, unbuilt until now), scoped narrowly to the axis-assignment table rather than the general named-preset system that remains Phase 2 territory. Persisting the table was judged worth it once Group switching multiplies one axis-target field into 40; which Group was last active was not, so it always starts at Group 1 — matching the "nothing else persists" precedent (`docs/llds/app-ui.md`'s Deferred section) until proven insufficient.
- **Intech Grid is one controller, not one profile per module.** PBF4 and VSN1 are module *definitions* the Grid Controller composes at runtime from whatever is physically connected, not separate user-selectable Controller Profiles — matching how a single nanoKONTROL Studio is one profile despite having many physical controls.
- **Logical controls, not raw CC/note numbers, are a Grid control's permanent identity.** Grid's own default ("MIDI Auto") addressing is derived from a module's position in the chain, so the same physical fader's raw CC number changes if the chain is rearranged or plugged in via a different module. DragonMIDI instead derives a stable logical-control identity (e.g. `("grid_fader", 3)`, read as "Grid Fader 3" — `docs/llds/intech-grid.md § Logical Control Identity`) from topology plus module type plus element index, and resolves incoming raw MIDI back to that identity on every event, rather than treating a CC number as a fader's name the way a Controller Profile's static table does.
- **Topology is read over Grid's own USB-serial control channel, independent of MIDI.** Grid exposes module position/hardware-type data over a second USB interface (a CDC serial port carrying periodic heartbeat broadcasts), not over MIDI itself; the Grid Topology Link opens and decodes that channel directly rather than requiring Intech's own Grid Editor application to be running.
- **A linear, single-row topology for Phase 7, normalized by X coordinate.** Modules report absolute X/Y grid coordinates that shift depending on which module is plugged into the USB host port; sorting by X and re-indexing from 0 makes the resulting left-to-right logical order independent of that absolute offset, so rearranging which module is the USB root doesn't change any module's logical identity.
- **Grid normalizes into the same logical-control identity the Mapping Engine already consumes, rather than bypassing it.** Grid-specific knowledge (topology, module definitions, the position-derived addressing formula) is confined entirely to the normalization step; once a raw Grid MIDI event resolves to a logical control, it drives Dragonframe through the same Mapping Engine/Bank/Group/Preset Store/Mapping View pipeline a static Controller Profile's controls already do, not a parallel, Grid-specific OSC path. This is practical specifically because `bank_count` is a controller-derived property rather than a DragonMIDI-wide constant fixed at 8 (see above): Grid's logical-strip count, computed at runtime from the connected chain, is just another value for that same property, so none of the Mapping Engine's Bank/Group math, the Preset Store's bounds, or the Mapping View's row count need to change for Grid to use them.
- **Grid's own documented position-derived MIDI Auto formula is reimplemented independently, not ported from Intech's source.** Intech's `grid-protocol`/`grid-fw`/`grid-editor` repositories are GPL-3.0-only (no "or later" grant), while DragonMIDI is GPL-3.0-or-later; rather than navigate that mismatch by copying code, DragonMIDI's Grid Controller independently implements the *documented facts* (the addressing formula, the module hardware-type IDs, the PBF4/VSN1 element tables) in original code, with comments citing where that knowledge came from for provenance.
- **Only PBF4 and VSN1 get module definitions.** Both are common, well-documented modules with stable element tables in Intech's own source; the rest of the Grid product line is unimplemented rather than guessed at from naming conventions.
- **Solo becomes Group-aware by changing its formula, not its target type.** Solo N already sends a fixed `select-AXN` unconditional on Bank/axis state (`MAP-WS-002`); Group switching changes only N's effective offset (`N + 8·(g-1)`) so Solo can reach any of the up to 40 addressable axes — it doesn't become Bank-derived and doesn't gain a second target type.
- **Control Descriptor is a presentation-layer unification, not a Mapping Engine change.** `ControllerProfile` (static YAML) and the Grid Controller (runtime-derived) already each produce a list of logical controls in their own shape; the Control Descriptor function reads from whichever is active and produces one common `(id, label, control_type, bank)` list for the Controller view and Table View to render, rather than teaching the Mapping Engine a third controller-description format or rewriting either existing one. Chosen over generalizing `ControllerProfile` itself to also describe Grid (would force a static schema onto Grid's runtime-only topology, reopening Phase 7's reasons for keeping Grid a separate `ActiveController` shape) and over giving the UI controller-specific branching per widget (exactly what §4 of the UI redesign task asks to avoid).
- **Inspector Editor Registry is keyed by `control_type`, not by controller or by target type.** A registry entry says "here is the editor for any fader," not "here is the editor for the nanoKONTROL Studio's Fader 3" or "here is the editor for OSC axis targets" — matching the roadmap's requirement that adding a behavior (center-stop shuttle, absolute-knob jog) later is a new registry entry, not new per-controller or per-target-type conditionals in the Controller view. Only one entry (`fader` → axis-target editor) exists after Phase 8; an unregistered `control_type` renders its existing read-only summary with no settings editor, rather than a dead or fake-looking control.
- **Table View is the prior Mapping View + Configuration Dialog, not a new third surface.** Preserving the existing widgets verbatim (rather than rebuilding an equivalent table from the Control Descriptor) keeps every existing Table View behavior — MIDI-learn, the fader Axis/Encoder mode switch, preset load/save — working exactly as before with zero re-implementation risk, at the cost of Table View and the Controller view being two separate widget trees over one shared engine rather than one widget tree in two layouts. Revisit only if maintaining two widget trees becomes the harder problem.
- **The Controller view and Table View share state through `MappingEngine`'s existing methods and `mapping_view_model.py`'s existing pure functions, not through each other.** Neither UI surface reads the other's widget state directly; both call the same existing `set_axis_target`/`clear_group_axis_target`/`axis_picker_state`/`group_axis_picker_states`, so an edit made in either is immediately visible to the other on next render — the same "one Mapping Engine instance" precedent already used for Group state and the Preset Store (see above), extended to cover the two presentation surfaces introduced in Phase 8. No new engine API was needed: these calls were already method-based, not raw dict access, so Phase 8 only adds a caller, not a new access path.
- **Host/port editing gets a new Settings dialog, not the existing Configuration dialog.** The two are different kinds of content — network configuration (machine-specific, rarely touched) versus per-control mapping summaries (part of the mapping data itself) — and the existing Configuration dialog already has an established identity as the latter, reachable from Table View. Folding host/port fields into it would conflate "where do I review my mapping" with "where do I point this app at Dragonframe," the same distinction the HLD's System Design already draws between these fields and the opinionated control mapping. The Settings dialog is a thin new container; no new validation or Apply logic is introduced — it hosts the Status window's existing fields verbatim.
- **The Group selector's A–E labels are the existing `_GROUP_LETTERS` Group mechanism, not a new "layer" concept.** The UI redesign task's "layer" language maps directly onto Phase 6's existing Group dimension, which the UI already labels A–E (`mapping_widgets.py`'s `_GROUP_LETTERS`); Phase 8 moves that label row from inside the Table View's grid to the Controller view's header as a standalone selector, without introducing a second, differently-named switching mechanism alongside it.

- **Named Controller identity is a module-type shape, never a per-module serial number — because no per-module serial number exists.** Direct inspection of Grid's heartbeat protocol (`docs/llds/intech-grid.md § Runtime Topology Model`) confirms the wire format carries no stable per-module identifier; a module's only identity within one session is its settled `(x, y)` position, which is positional and resets on every rearrangement by design (the existing USB-root normalization already treats raw position as non-identity). Named Controller matching therefore keys on the coarser, but actually stable, module-*type* sequence instead — accurate enough to tell "a PBF4+VSN1+PBF4 chain" apart from "a PBF4+PBF4+PBF4 chain," but unable to tell two different physical PBF4+VSN1+PBF4 rigs apart from each other, which is why a shape-match ambiguity (two or more saved Named Controllers sharing one shape) is surfaced to the user rather than resolved automatically. Chosen over waiting for Intech to add a serial-number field to the protocol (not DragonMIDI's to request) or inventing a local pseudo-identity by writing a value into a module's own configuration (out of scope — Grid topology discovery is read-only, per the existing Non-Goals).
- **The single-VSN1 restriction is lifted by generalizing, not special-casing.** Phase 7 originally rejected a second VSN1 outright because its buttons/jog used a singular `("grid_vsn1_button", N)`/`("grid_vsn1_jog", None)` identity that a second module would silently alias. Rather than add a new per-instance key dimension, VSN1's elements now number globally left-to-right across every VSN1 present, exactly the scheme PBF4's faders/pots/buttons already use across multiple PBF4 modules (`docs/llds/intech-grid.md § Module Definitions`) — `("grid_vsn1_jog", None)` becomes `("grid_vsn1_jog", N)` for the Nth VSN1 (`1` for a single VSN1, equivalent in every way that matters since nothing is persisted under the old `None`-shaped key today — no `opinionated_map` entry, no Mapping View row exists for VSN1's jog/buttons yet, `docs/llds/intech-grid.md § Persistence`). This is why lifting the restriction is safe to do directly rather than behind a compatibility shim.
- **Discovery reliability for Korg stays name-based; USB VID/PID was investigated and set aside.** Neither `mido` nor `python-rtmidi`'s backends (CoreMIDI on macOS, the Windows MIDI services backend) expose a MIDI endpoint's originating USB VID/PID without new, platform-specific code (CoreMIDI entity-property queries or an IOKit walk on macOS; a WinRT/`SetupAPI` path on Windows) — a real new dependency surface for a signal that would only ever corroborate, not replace, name matching, which the two bundled Korg profiles already use successfully. This is the same conclusion the Intech Grid LLD already reached for Grid's own MIDI port (`docs/llds/intech-grid.md § Controller-Defined bank_count and MIDI-Port Discovery`) — kept consistent rather than re-opened per controller family.
- **The Controller view's module grouping for Grid is additive to `GridRuntimeController`, not a new resolution path.** `address_table` (`docs/llds/intech-grid.md § MIDI → Module/Element Resolution`) already discards which physical module a resolved logical key came from — sufficient for Phase 1's event routing, insufficient for a module-grouped control list. `GridRuntimeController` gains a second, read-only field recording each logical key's owning module (its normalized left-to-right ordinal and recognized type), populated at the same construction step that already walks the ordered modules — the Control Descriptor (`docs/llds/app-ui.md § Control Descriptor and Inspector Editor Registry`) and `control_grouping.py` read this to nest Grid's control list by module, then channel, then control, while a Korg profile (which has no modules) keeps its existing flat Bank/Channel grouping unchanged.
- **Named Controller generalizes into Named Configuration: many per hardware key, not exactly one.** The prior "one `NamedController` per `profile_name`/`module_shape`" assumption is lifted — that field becomes a hardware key zero or more saved configurations can share, with Save As the normal way to create a second one. No new registry or file format: `named_controller_registry.py`'s existing records, folder, and one-file-per-`id` convention are reused directly; it gains only a hardware-key filter (`configurations_for(hardware_key)`) and one new field (below). Chosen over a separate Named Configuration layer referencing `NamedController` as an anchor (a second persisted registry for the same information) — see the options considered during this phase's design.
- **`is_builtin` protects the auto-created default from direct overwrite.** The record `ensure_static_named_controller()` creates for a Korg profile, and the one the legacy-migration path creates for a pre-existing Grid installation (`docs/llds/named-controller.md §§ 2, 5`), are flagged `is_builtin=True` at creation and never afterward. Save while a builtin is active prompts for a name and performs a Save As instead of overwriting it; every other record defaults to `is_builtin=False` and Save behaves normally. `rename_named_controller` is unaffected — renaming a builtin's `display_name` still never touches its `id` or its file, exactly as before.
- **Save, Save As, and Load are explicit actions scoped to "configurations sharing the active hardware's key," distinct from the Controller dropdown.** The dropdown still only selects hardware (a `ControllerProfile` or Intech Grid) — unchanged. A new control cluster beside it operates one level below: Save writes the active configuration's current mapping; Save As prompts for a name and creates a sibling `NamedController` under the same hardware key; Load reuses the existing Ambiguous-dialog-style list widget (`named_controller_dialog.py`), now also opened on demand rather than only when a real shape collision forces it, listing every saved configuration for the active hardware key.
- **Grid's automatic connect-time zero/one/many resolution keeps its existing safety behavior unchanged.** Two or more saved configurations sharing a `module_shape` is now the ordinary outcome of deliberate Save As use, not only an accidental collision — but `resolve_grid_named_controller()` still blocks and asks on every such match at topology-settle time; nothing about when that automatic dialog fires, or its refusal to guess, changes. Save/Save As/Load are additional user-driven entry points into the same registry, not a replacement for the connect-time path.
- **Unsaved-change tracking is a dirty comparison against the last loaded/saved snapshot, not a new undo mechanism.** The active configuration's in-memory (Bank, Group) axis table and bank actions are compared to the snapshot taken at the last successful Load or Save; a difference is "unsaved changes," prompting before a Controller-dropdown switch or a Load discards them. No history of intermediate states is kept.
- **Load validates an Intech configuration's stored topology before applying it.** A `kind="grid"` configuration's `module_shape` (fixed at creation) is compared against the currently settled topology's shape; a mismatch refuses the load with a clear message rather than applying a (Bank, Group) axis table built for different physical hardware onto what's actually connected.

## Success Metrics

- Moving any enabled fader/knob/button lights the MIDI indicator within ~1 second and dims it again within a few seconds of going quiet.
- With Dragonframe's OSC Output pointed at DragonMIDI's listener, the Dragonframe indicator lights within ~1 second of any Dragonframe-originated OSC event.
- Querying `getAllPosition` against a project with configured axes returns responses that DragonMIDI correctly parses into that project's exact axis names.
- A fader mapped to a discovered axis, with a configured min/max range, produces `gotoPosition` messages scaled correctly into that range on every distinct value, with no debounce.
- Every control in the default preset produces the identical OSC address/argument shape as the prototype's `mappings.md` for the same physical control moves.
- The mapping view always reflects what the engine actually enforces: editing an assignment, restarting, and moving the control fires the *new* assignment, not the old default.
- Turning the jog wheel steps the timeline frame-by-frame both on the main Animation/Cinematography timeline (via OSC) and, with Dragonframe as the OS-focused app, inside the Arc Motion Control workspace (via the synthesized "Step Moco Forward"/"Step Moco Back" keystroke) — the latter has no OSC equivalent at all.
- A control mapped to a WebSocket target (`E-Stop`, `select-AXn`, or `jog-AXn`) sends the corresponding `{"input": "<name>"}` JSON command and Dragonframe recognizes it, verifiable via Dragonframe's debug log (e.g. `HARD STOP` for `E-Stop`).
- Falsification signal: either indicator lit while its channel has gone silent, or dark while traffic is genuinely flowing, means the liveness design has failed.
- Selecting nanoKONTROL2 from the Controller Profile dropdown and plugging one in brings the MIDI indicator live and drives Dragonframe via the nanoKONTROL2's default map, with jog-wheel- and Scene-button-only behaviors correctly absent rather than silently no-op.
- Dropping a correctly-formed Controller Profile config file into the user-local controllers folder and relaunching makes that controller appear in the dropdown and drive Dragonframe via its declared map — no rebuild, no code change.
- A user-local config file with the same name as a bundled one takes effect instead of the bundled one, provably (e.g. a deliberately-altered CC number in the user-local copy is the one that fires).
- Pressing Track ► while Group 1 is active switches to Group 2: the Group-2 indicator light replaces Group-1's, and every fader immediately drives whichever axis is assigned to its Bank under Group 2, not Group 1's prior axis.
- Restarting DragonMIDI after configuring axis assignments across all 5 Groups reloads the identical (Bank, Group) → axis table from `~/Documents/DragonMIDI/configurations/`; the active Group resets to Group 1 regardless of which Group was active at quit.
- Pressing Solo 3 while Group 2 is active sends `select-AX11` (`3 + 8·(2-1)`), not `select-AX3`.
- Connecting a PBF4 | VSN1 | PBF4 chain in any physical USB-root order and selecting Intech Grid from the Controller Profile dropdown exposes exactly 8 sequential Grid Fader logical controls (1–8), numbered left to right, with the VSN1 in the middle contributing none of them.
- Unplugging the chain from one end's PBF4 and reconnecting it from the other end (reversing which module is the USB root) does not change any control's logical identity or numbering.
- Moving the VSN1 to a different position within the row does not change the identity of "VSN1 Jog" or any "VSN1 Button N" — only which raw MIDI address currently reaches it.
- A raw MIDI message generated by the same physical control resolves to the same logical control before and after the chain is rearranged, even though its raw CC/note number differs between the two arrangements.
- Selecting nanoKONTROL Studio or nanoKONTROL2 continues to behave identically to before Intech Grid support was added — no shared code path regressed.
- Selecting Fader 1 in the Controller view's control list and setting its target axis/range in the Inspector produces the identical engine state as making the same edit in Table View — switching to Table View afterward shows the new assignment, not the old one, and vice versa.
- Each of the four supported controller families (nanoKONTROL Studio, nanoKONTROL2, PBF4, VSN1) populates the Controller view's control list with the correct count and type of controls (e.g. PBF4: 4 faders, 4 knobs, 4 buttons, no jog wheel; VSN1: 0 faders, a jog wheel, 8 buttons) with no controller-specific code in the control list or Inspector widgets themselves.
- Falsification signal: the Controller view and Table View ever disagree about a control's current assignment after an edit in either, without an intervening controller/profile switch — means a second mapping state has crept in.

- Connecting a never-before-seen Intech Grid shape activates immediately under a default name, with no dialog, exactly as connecting a Korg controller for the first time already does; the only prompt a user ever sees is when a shape genuinely matches more than one saved Named Controller.
- Connecting a saved "Stewart Platform Controller" arrangement a second time, after also having saved and used an unrelated, identically-shaped rig in between, requires picking which one applies — the Stewart Platform rig's saved axis table never silently loads onto the unrelated rig.
- A `PBF4 | VSN1 | PBF4 | VSN1` chain builds a working Grid controller with 8 sequential Grid Faders and correctly, globally-numbered buttons/jog across both VSN1 modules — not a construction failure.
- The Controller view's control list for a `PBF4 | VSN1 | PBF4` chain shows three module groups (two PBF4, one VSN1) in left-to-right order, each containing only its own controls, rather than one flat Bank-numbered list spanning all three.
- A user can Save As a second named configuration for the same hardware (same `profile_name` or `module_shape`) as an existing one, see both listed, and Load either one back — the mapping that results is the one that was saved under the chosen name, never a different saved configuration's.
- Pressing Save while a built-in default configuration is active prompts for a new name (Save As) instead of silently rewriting the built-in's file; the built-in configuration is unaffected and remains selectable afterward with its original mapping intact.
- Switching the Controller dropdown, or pressing Load, while the active configuration has edits not yet saved warns before discarding them; choosing to proceed discards them, choosing to cancel leaves the current configuration and its edits exactly as they were.
- Loading a saved Intech Grid configuration whose stored module-type shape does not match the currently connected hardware's settled shape is refused with a clear message — it is never silently applied onto mismatched topology.
