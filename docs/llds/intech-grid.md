# Intech Grid Support

## Context and Design Philosophy

Continues `docs/high-level-design.md § Delivery Phasing` (Phase 7) and `§ Key Design Decisions`' Intech Grid entries. This LLD owns everything between "an Intech Studio Grid chain of PBF4/VSN1 modules is connected" and "the Mapping Engine (`docs/llds/static-mapping.md`) receives ordinary logical-control events" — it does not own anything downstream of that handoff (Bank/Group math, the Preset Store, the Mapping View), which are `static-mapping.md`'s and `app-ui.md`'s territory, unchanged by this document.

**Grid is architecturally unlike every existing Controller Profile**, for one reason: a Controller Profile's shape (which CCs exist, how many channel strips) is a fixed fact about one physical device, declared once in a YAML file and never rediscovered. Grid's shape is a fact about *today's physical arrangement* of interchangeable modules, discovered fresh each time the chain is connected, over a channel MIDI itself doesn't carry (topology). Forcing Grid through the YAML `ControlsConfig`/`ControllerProfile` path would mean either inventing a fake static profile that lies about a fact (device shape) that isn't static, or teaching the config-file format to describe something it was never meant to express (a runtime-discovered topology). Neither is this LLD's approach — see Active Grid Controller below.

**This document's governing constraint, inherited from the HLD**: Grid-specific knowledge — topology, module definitions, the position-derived MIDI addressing formula — is confined entirely to the components this LLD defines. The moment an incoming Grid MIDI event resolves to a logical control, it is handed to the *existing* Mapping Engine exactly as a Korg profile's own `(type, number)` keys already are. Nothing downstream of that handoff needs to know Grid exists. This is why `ControllerProfile.bank_count` becoming controller-derived (rather than a hardcoded `8`) was a prerequisite refactor completed before this LLD was drafted — Grid's runtime-discovered width is now just another value for a property every consumer already reads generically.

**This revision's governing addition: fail closed, always.** The previous draft tolerated several forms of ambiguity (unknown modules silently excluded regardless of position, address collisions resolved by "last one wins," structural topology drift left for a stale `address_table` to keep serving). This revision replaces every one of those with an explicit, closed failure: if Grid's current physical/topological state cannot be interpreted with certainty, DragonMIDI does not guess — it refuses to activate (or deactivates) the Grid controller and says so, rather than silently acting on a subset of what's connected or a stale resolution of it.

**Scope: Phase 1 only.** A single horizontal row of any collision-free combination of supported modules, zero or one VSN1, factory-default MIDI Auto addressing (including whichever page is actually active, read from the protocol — not merely assumed), no live structural rebuild. See Non-Goals below for the complete exclusion list.

**Naming note, for readers coming from the HLD's System Design diagram.** The HLD draws two coarse-grained boxes, `GRIDTOPO` ("Grid Topology Link") and `GRIDCTRL` ("Grid Controller"). This LLD's finer-grained components map onto them as: `GRIDTOPO` ≈ §1 (Grid CDC Transport) + §2 (Grid Frame / Heartbeat Parser) + §3 (Runtime Topology Model); `GRIDCTRL` ≈ §4 (Module Definitions) + §5 (Active Grid Controller, i.e. `GridRuntimeController`) + §6 (MIDI → Module/Element Resolution). No architectural claim rides on this split — it exists only so this document's class-level detail doesn't need a name for every HLD box, and a reader shouldn't expect to find literal classes called `GridTopologyLink`/`GridController` anywhere below.

## 1. Grid CDC Transport

Grid exposes two independent USB interfaces (source: `grid-fw/d51n20a/grid/d51/tusb_config.h`): a standard USB-MIDI class interface, carrying ordinary Note/CC traffic DragonMIDI already knows how to read (`docs/llds/midi-input.md`'s `MidiBackend`/`normalize_raw()`); and a USB-CDC virtual serial port at **2,000,000 baud**, carrying Grid's own ASCII-framed protocol (topology heartbeats, Lua scripting, LED control, etc.) — DragonMIDI needs only the heartbeat subset of this second channel.

**No Grid Editor dependency.** Grid Editor opens the CDC port itself via the browser's Web Serial API, filtered by a plain VID/PID allowlist in its own `configuration.json` — nothing about this is a proprietary handshake. A standalone client opening the same port directly needs nothing else running.

- **`GridTransport`**, a `Protocol` parallel to `midi_input.py`'s existing `MidiBackend` (`list_inputs`/`open_input`/`list_outputs`/`open_output`): `list_candidate_ports() -> list[str]` (serial ports matching Grid's known VID/PID pairs), `open(port_name: str, callback: Callable[[bytes], None]) -> GridConnection` (callback receives raw byte chunks as they arrive, mirroring `open_input`'s per-message callback shape), `close()`.
- **`SerialGridTransport`**, the real implementation, backed by `pyserial` (a new dependency — not yet in `pyproject.toml`; adding it is Phase 2 implementation work, not this LLD). Opens at 2,000,000 baud. **Primary signal: VID/PID.** Port candidates are filtered against the VID/PID pairs grid-editor itself uses (source: `grid-editor/configuration.json`) — `(0x03eb, 0xecac)`, `(0x303a, 0x8123)`, `(0x2e8a, 0x1145)`. **Secondary signal: the CDC port's name.** Source research had assumed Grid's shared USB descriptor source (`grid-fw/common/src/c/grid_usb.c`) would give the CDC interface its own descriptor string, `"Intech Grid CDC"`, distinct from the device's bare product string (`"Grid"`). **Corrected against real hardware (2026-11-04):** the real CDC port's description/product string (confirmed via pyserial's `list_ports`) is simply `"Grid"`, the bare product string — not a distinct per-interface string. This was never functionally load-bearing (VID/PID already succeeds without it; this corroboration is optional and its absence never disqualifies an otherwise-matching VID/PID), but the match substring is now `"grid"` so the corroboration can actually fire.
- **Discovery/reconnect**: mirrors `MidiInputAdapter.poll_discovery()` — poll candidate ports on a timer, treat a read failure or the port vanishing from the list as a disconnect, resume polling. No new concurrency model; this is the same single-loop, serially-executed pattern `midi-input.md`'s Device Discovery and Auto-Connect section already specifies, applied to a second transport.
- **More than one candidate port is ambiguous, not "take the first."** Korg's existing precedent — connect to the first of several duplicate-matching MIDI ports, log the choice — assumes two physically identical, interchangeable units. Grid breaks that assumption: two matching CDC ports could be two entirely different rigs with different module sets, and guessing which one the user meant to use is exactly the kind of silent misinterpretation this revision eliminates. **If more than one Grid CDC candidate is found, the transport does not open any of them** — it reports an ambiguous-chains state (§11) and Grid does not become active until only one candidate remains (the user disconnects one; a future phase may add explicit selection — Non-Goals, Open Questions).
- **Not over-designed**: beyond the ambiguity rule above, a single candidate port is simply connected to. No platform-specific USB enumeration beyond what `pyserial`'s own cross-platform port listing already provides.

## 2. Grid Frame / Heartbeat Parser

**Wire format — corrected against real hardware (2026-11-04 validation pass; see the completion report).** An earlier draft of this section (and of `grid_protocol.py`) assumed a single flat `SOH 'H' TYPE HWCFG SX SY ROT PORTROT EOB` record. Capturing and decoding real CDC traffic from a physical PBF4/VSN1 chain showed the real wire format is a two-level **"BRC" packet** instead, confirmed against Intech Studio's own `grid-protocol` TypeScript source (`src/grid-protocol.ts`'s `decode_packet_frame`, GPL-3.0-only, independently reimplemented — no source lines copied):

    SOH BRC(0x0F) <20 ASCII-hex header fields> EOB <class block>+ EOT <checksum(2)> LF

The 20-byte **BRC header** (field offsets counted from the packet's own `SOH`, always 23 bytes total through `EOB` at index 22) carries `LEN`/`ID`/`SESSION`/`DX`/`DY`/`MSGAGE` (not read — not load-bearing for anything this module's consumers do) alongside the fields DragonMIDI does read: `SX`/`SY` (the module's own position, **1 byte/2 hex digits each, biased by +127** — not the 4-hex-digit two's-complement field the earlier draft assumed) and `ROT`/`PORTROT` (1 hex digit each). Each **class block** is `STX <3-hex class code> <1 reserved byte> <fields> ETX` (field offsets counted from that block's own `STX`); only two class codes matter for Phase 1 — `HEARTBEAT` (`0x010`: `TYPE`, `HWCFG`, plus `VMAJOR`/`VMINOR`/`VPATCH`/`PORTSTATE`/`GCCOUNT`, read but not used) and `PAGEACTIVE` (`0x030`: `PAGENUMBER`), the latter present only alongside a `TYPE == 1` heartbeat. A packet's trailing checksum (XOR of every byte except its own 2 trailing hex digits) is verified — real hardware's own noise-rejection, newly added by this correction — but `LEN` is not independently checked, unlike Intech's own decoder; checksum verification already covers DragonMIDI's own correctness concern and `LEN` would be redundant with it.

**None of this changes anything above the byte layer.** `GridHeartbeat`'s shape, the `TYPE`/`PAGEACTIVE` semantics below, and every downstream module (topology, controller, lifecycle) are completely unaffected — they only ever consumed `GridHeartbeat` objects, never raw bytes. The correction was confirmed by feeding a real 3-second capture (24 consecutive packets, 2×PBF4 + 1×VSN1) through the corrected parser with zero failures and all checksums valid; a frozen sample of that capture is now a permanent regression fixture (`tests/test_grid_protocol.py`).

**Corrected `TYPE` handling (this revision).** The previous draft treated `TYPE=1` as the only kind of heartbeat worth keeping, filtering out everything else as "not a module DragonMIDI needs." That was wrong: `TYPE=0` ("grid") and `TYPE=1` ("gridmaster") are **both real, physically-present Grid modules** — `0` is every ordinary module in the chain, `1` is specifically the one module plugged directly into the USB host port (the bus master, and by construction the module at absolute position `(0, 0)`). Grid Editor itself builds its topology view from the *entire* heartbeat set, not from `TYPE=1` alone, and DragonMIDI must do the same: **every `TYPE=0` or `TYPE=1` heartbeat contributes a module to the topology; every other `TYPE` value — `255` ("editor" — Grid Editor announcing its own presence, not a Grid module at all) explicitly, and any other value the protocol might someday carry — is recognized as "not a module" and discarded, never treated as a crash or a third kind of module.** `TYPE` is retained as metadata on `GridHeartbeat`/`GridModule` (useful for diagnostics — confirming which module is the USB-connected root) but, for the two known-module values, is never used to exclude an otherwise-valid module from topology.

**A second, valuable fact rides along on the `TYPE=1` heartbeat specifically: the currently active page.** Source-confirmed in `grid-fw/common/src/c/grid_transport.c`: the firmware's periodic heartbeat-broadcast routine appends a second frame, `PAGEACTIVE` (carrying the current page number), to the *same* transmission, but **only when `type == 1`** — i.e. only the gridmaster reports it, piggybacked on its own heartbeat, every ~250ms, unconditionally. This means DragonMIDI can read Grid's actual current page directly from data it is already parsing, rather than merely assuming page `0` — see §6 for why this matters for the addressing formula, and §3 for how it becomes part of a settled `GridTopology`.

**Scope: only what DragonMIDI needs.** `VMAJOR`/`VMINOR`/`VPATCH`, `PORTSTATE`, `GCCOUNT`, and every non-heartbeat, non-`PAGEACTIVE` frame type (Lua scripting, LED/display control, configuration read/write, `PAGECOUNT`, etc.) are not parsed at all. This is the same "normalize what we use, ignore the rest" posture `midi_input.py`'s `normalize_raw()` already takes toward MIDI message types DragonMIDI's mapping never consumes.

- **`GridHeartbeat`** (frozen dataclass): `heartbeat_type: int` (`0`, `1`, or `255` — retained as metadata, see above), `hwcfg: int`, `x: int`, `y: int`, `rotation: int`, `port_rotation: int`, `page: int | None` (the `PAGEACTIVE` value, present only when `heartbeat_type == 1`; `None` otherwise). Produced for `heartbeat_type in (0, 1)` only; a frame reporting any other `heartbeat_type` (`255`/editor, or any value the protocol does not yet define) is recognized as not a module and produces nothing, the same as a frame that fails to parse outright.
- **Frame boundary handling**: a small accumulator state machine — `WAITING_FOR_SOH` → (byte-by-byte) → `ACCUMULATING` (buffering until `LF`, the real packet terminator — corrected from an earlier, wrong assumption that `EOB` itself ended the packet; `EOB` only ends the BRC header, with class blocks and a checksum following it before `LF`) → attempt-parse → back to `WAITING_FOR_SOH`. On any failure (a malformed packet, a checksum mismatch, a buffer that grows past a sane maximum packet length with no `LF` seen, fields that don't parse as the expected hex digits) the accumulator discards its buffer and returns to `WAITING_FOR_SOH` — it never raises, matching the Grid CDC Transport's "never crash on malformed input" posture already established for raw MIDI (`normalize_raw()` returns `None`, never raises, for anything it doesn't recognize). This also correctly handles a packet split across two serial reads (bytes simply keep accumulating across calls, confirmed byte-by-byte against the real capture) and multiple packets delivered in one serial read.
- **Provenance**: the field *offsets* and frame *delimiters* are protocol facts, independently reimplemented in Python from Intech's own `grid-protocol` TypeScript source and confirmed against a real captured byte trace (not ported code — see Licensing/Provenance below).
- **Thread safety (found during application-integration wiring, not a Phase-1-parser-level issue but noted here since it's this same accumulator's caller):** the real `SerialGridTransport` reads on a background thread and invokes its callback from that thread; `GridLifecycle` queues incoming bytes and only ever touches this accumulator from the thread that calls its own `poll()` (the Qt main thread) — see `docs/llds/intech-grid.md § 14. Application Integration`.

## 3. Runtime Topology Model

- **`GridModule`** (frozen dataclass): `heartbeat_type: int`, `hwcfg: int`, `module_type: ModuleType | None` (`None` for an unrecognized `hwcfg`, see Module Definitions below), `x: int`, `y: int`, `rotation: int`.
- **`GridTopology`** (frozen dataclass): `modules: tuple[GridModule, ...]`, `current_page: int` (read from the gridmaster's heartbeat — see §2; a settled `GridTopology` always has this populated, per the settle precondition below).
- **Module-type derivation**: `module_type_from_hwcfg(hwcfg: int) -> ModuleType | None`, a plain dict lookup against the exact source-verified table (Module Definitions below). An unrecognized `hwcfg` doesn't, by itself, fail topology construction — see the Unsupported-Module Policy bullet below for the exact (and now stricter) rule.
- **Snapshot assembly**: there is no stable per-module serial number in the heartbeat payload — a module's identity *is* its `(x, y)` position, since no two modules can occupy the same slot. A `GridTopologyBuilder` accumulates the most recent heartbeat per `(x, y)` slot (for both `heartbeat_type` 0 and 1 — see §2) and drops a slot whose heartbeat hasn't refreshed within Grid's own disconnect timeout (500ms, source: `GRID_PARAMETER_UART_DISCONNECTTIMEOUT_us`, `grid_protocol_bot.json`) — reusing Grid's own liveness constant rather than inventing a new one.
- **Structural change vs. ordinary refresh — the definition §7 (Topology Change Policy) and the settle rule below both depend on.** A heartbeat for an `(x, y)` slot already in the builder's current snapshot, reporting the *same* `hwcfg` and `rotation` it already had, is an **ordinary refresh** — it only resets that slot's liveness clock and otherwise changes nothing. Any of the following is a **structural change**: a new `(x, y)` slot appearing; an existing slot's heartbeat timing out (disappearing); an existing slot reporting a *different* `hwcfg` or `rotation` than it last had; the gridmaster's reported `current_page` changing. Nothing else counts — a module that simply keeps heartbeating unchanged, however many times, is never itself a structural change.
- **"Topology is ready" (settling)** is defined by this structural-change distinction, not by elapsed time since the first heartbeat: the builder waits for a settle window (proposed **`GRID_TOPOLOGY_SETTLE_SECONDS = 0.5`**, named and centralized rather than a scattered literal — see Decisions & Alternatives for why 500ms, and Open Questions for its tunability) during which **no structural change occurs**, and during which **at least one gridmaster (`heartbeat_type == 1`) heartbeat has been seen** (needed both to confirm a USB root exists at all and to populate `current_page`). An ordinary refresh of an already-known, unchanged module does **not** restart this window; a structural change (by the definition above) does. Before both conditions hold, there is no settled `GridTopology` at all.
- **USB-root normalization — the core correctness rule this LLD exists to satisfy**: `x`/`y` are *absolute* coordinates relative to whichever module is plugged into the USB host port (the gridmaster, always `(0, 0)`) — replugging the chain from a different end shifts every module's absolute `x` by a constant offset, without changing the physical left-to-right arrangement at all. **DragonMIDI never treats absolute `x` as identity.** `normalize_linear_order(modules) -> tuple[GridModule, ...]` sorts strictly by `x` ascending and the result's *position in that sorted sequence* — not the `x` value itself — is what every downstream numbering rule (Module Definitions, Logical Control Identity) is built from. Two topologies differing only by a constant offset to every module's `x` produce an identical `normalize_linear_order()` result. **This is a separate concern from MIDI address resolution (§6), which deliberately keeps using raw, un-normalized `x`/`y`** — Grid's own firmware computed its addresses from absolute coordinates before DragonMIDI ever saw the data, so inverting that formula must use the same absolute coordinates, never the normalized rank. Logical *identity* uses rank; MIDI *address resolution* uses raw `x`/`y`. Conflating the two would make either normalization or resolution wrong.
- **Single-row validation applies to every detected module, recognized or not — this is the corrected Phase-1 policy.** The previous draft silently excluded a module with a different `y` from normalization, the same treatment given to an unrecognized `hwcfg`. That's no longer correct: if *any* detected module (supported type or not) reports a `y` different from the rest, the chain is not Phase 1's single supported row, full stop — DragonMIDI must not silently interpret only the subset that happens to share one row, since the user would then be unknowingly controlling less than what's actually connected. **This check runs against the complete detected module set, before module-type recognition is even consulted**, and a failure here is a hard Grid-initialization failure (§5's `GridControllerBuildOutcome.UnsupportedTopology`), not a partial/degraded result. Only *after* the whole set is confirmed a single row does module-type recognition apply — an unsupported module *within* an already-confirmed single row is excluded from element enumeration (it contributes no logical controls) but does not invalidate the row, because by that point its presence can no longer make the row's left-to-right order ambiguous: sorting the recognized modules by `x` is unaffected by the presence or absence of an unrelated entry in the same list. See Decisions & Alternatives and the Edge-Case Audit (below, in the project's completion report) for the reasoning this distinction rests on.

## 4. Module Definitions

Module definitions are **templates**, not Controller Profiles — never user-selectable, only composed at runtime from whatever `module_type_from_hwcfg()` resolves.

- **`GridElement`** (frozen dataclass): `index: int` (the element's 0-based index within its module, exactly as Intech's own firmware numbers it), `role: str` (`"fader"`, `"potentiometer"`, `"button"`, `"endless"`, `"jog_button"`, or `"lcd"`).
- **`GridModuleDefinition`** (frozen dataclass): `name: str`, `hwcfg_values: frozenset[int]`, `elements: tuple[GridElement, ...]`.

**`PBF4_DEFINITION`** (source: `grid-protocol/src/grid-protocol.ts` `moduleElements[ModuleType.PBF4]`, independently reimplemented — see Licensing/Provenance):

```text
hwcfg_values = {64, 65, 67, 75}   # PBF4 RevA/RevD/RevH/CD_RevH

index 0-3   role="potentiometer"
index 4-7   role="fader"
index 8-11  role="button"
# index 255 ("system") is not a real I/O control and is not part of this definition
```

**`VSN1_DEFINITION`** (source: `grid-protocol/src/grid-protocol.ts` `moduleElements[ModuleType.VSN1L / VSN1R]`, identical for both — independently reimplemented):

```text
hwcfg_values = {49, 81, 57, 89, 59, 91}   # VSN1L/VSN1R x RevA/RevB/RevH

index 0-7    role="button"
index 8      role="endless"       # turning it: CC on this index
index 8      role="jog_button"    # pressing it straight down: Note On/Off on the SAME index
index 9-12   role="button"
index 13     role="lcd"
# index 255 ("system") is not part of this definition
```

**Index 8 carries two elements — confirmed against real hardware (2026-11-04 validation), not source-derived.** Neither `grid-protocol.ts` nor any other source consulted during design documents that the endless encoder has its own push-button; this was discovered only by physically pressing it during hardware validation and observing a `Note On`/`Note Off` pair on the same raw MIDI number the encoder's own `CC` uses. `_raw_key_for()` (§6) disambiguates the two purely by message type (`"note"` for `"button"`/`"jog_button"` roles, `"cc"` otherwise) exactly as it already does for every other button role — no index-based special-casing was needed. The push-button gets its own stable logical identity, `("grid_vsn1_jog_button", None)` ("VSN1 Jog Push"), the same singular `(tag, None)` shape `grid_vsn1_jog` already used (at most one per VSN1, no counted index needed).

**Normalization rule, stated precisely**: PBF4's faders, potentiometers, and buttons each number **1..N left-to-right across every PBF4 module in the normalized row, independently of one another** — a module in between (VSN1, or an unsupported module) never resets or interrupts any of the three sequences.

**VSN1 multiplicity, revised Phase 1.3: numbered globally, the same way PBF4 already is, not restricted to zero-or-one.** The original Phase 1 restricted a topology to at most one recognized VSN1, because VSN1's buttons/jog used a *singular* logical identity (`("grid_vsn1_button", N)` for `N` 1..12 within the one allowed module, `("grid_vsn1_jog", None)`) that a second VSN1 would silently alias — a real logical-identity collision, distinct from the raw-MIDI-address collision §6 already detects (two VSN1s' raw addresses legitimately differ, since they sit at different `x` positions, so `AddressCollision` would not necessarily catch it). Phase 1.3 lifts the restriction by generalizing instead of special-casing further: VSN1's buttons now number **globally left-to-right across every recognized VSN1 module in the normalized row**, exactly PBF4's own per-tag numbering scheme — module 1's 12 buttons are 1..12, module 2's are 13..24, and so on — and VSN1's jog/jog-button gain a **VSN1-instance ordinal**, `("grid_vsn1_jog", M)`/`("grid_vsn1_jog_button", M)` where `M` is 1 for the first recognized VSN1 in left-to-right order, 2 for the second, and so on (replacing the old singular `None` second element — safe to change outright, not behind a compatibility shim, because nothing is persisted under the old shape today: no `opinionated_map` entry and no Mapping View row exist for VSN1's jog/buttons yet, `§ Persistence` below). A single VSN1 still gets `M = 1` — identical behavior to before in every way that matters, since the old `None` was never read by anything that distinguished it from an integer. **Accepted limitation, stated precisely so it isn't mistaken for an invariance guarantee**: with exactly one recognized VSN1, its ordinal is always `1` regardless of position, matching the original Phase 1/1.2 guarantee that a lone VSN1's identity never depends on where it sits in the row; with two or more recognized VSN1 modules, reordering their *relative* left-to-right positions reassigns which ordinal (and therefore which `("grid_vsn1_jog", M)`/button-number range) each gets — the same positional-not-persistent limitation already accepted for Bank numbering (`§ Persistence`), not a new one, and not something this revision claims to solve. `control_names` display text follows the same split already used for PBF4's module-grouped UI labels (`docs/llds/app-ui.md`): a lone VSN1 is still labeled plainly ("VSN1 Button 3," "VSN1 Jog"); a second or later VSN1 present in the same topology is labeled with its ordinal ("VSN1 #2 Button 3," "VSN1 #2 Jog") so the two naming schemes never collide when going from one VSN1 to two. See `GridControllerBuildOutcome` below for why this is no longer a construction-time rejection.

**`VSN1L`/`VSN1R` collapse to one definition.** Both hardware IDs resolve to the same `VSN1_DEFINITION` via `module_type_from_hwcfg()` — their element tables are identical regardless of which side the LCD sits on, and nothing in the source evidence suggests a behavioral distinction worth making.

**`role="lcd"` is recorded but produces no logical control in Phase 1** (Non-Goals: no display output). It's kept in the definition for completeness and because a future phase giving VSN1 output capability shouldn't need to re-derive the element table from source again.

`MODULE_DEFINITIONS = (PBF4_DEFINITION, VSN1_DEFINITION)`. An `hwcfg` matching neither is `module_type_from_hwcfg()`'s `None` case — handled per the Unsupported-Module Policy in §3 above (excluded from element enumeration once the row is confirmed valid; invalidates the row if it's what made the row's `y`-uniformity fail).

**PBF4's potentiometer and button are bank-derived, like a Korg profile's Knob/Mute (Phase 1.2, `GRID-CTRL-011`).** `build_grid_controller()` pairs `("grid_pbf4_pot", i)`/`("grid_pbf4_button", i)` with `("grid_fader", i)` for `i` from 1 through `bank_count`, populating `knob_to_fader`/`mute_to_fader`/`fader_to_knob` on `GridRuntimeController` — empty for a VSN1-only topology, same as before Phase 1.2. This is sound because every PBF4 module contributes exactly one potentiometer, one fader, and one button per channel, numbered in the same per-module order (§ above); `i`'s pot/fader/button are therefore always the same physical channel strip, across any number or order of PBF4 modules mixed with VSN1 modules (whose elements never touch these three counters). `docs/llds/static-mapping.md § Bank Derivation` and `§ Independent Rotary/Button Action Assignment` then apply to PBF4 with no Grid-specific branch — the same code path Korg's Knob/Mute already use.

**Module membership and shape (Phase 1.3 addition, additive only — no existing field's meaning changes).** Two new pieces of information are derived at the same construction step that already walks the normalized module order, for two consumers outside this LLD's own territory:

```text
module_shape: tuple[str, ...]          # recognized module-type names, left-to-right, e.g. ("PBF4", "VSN1", "PBF4")
control_module: Mapping[_Key, ModuleRef]   # every recognized logical key -> which module it came from
ModuleRef = NamedTuple("ModuleRef", [("ordinal", int), ("module_type", str)])
```

`module_shape` is read by `docs/llds/named-controller.md § Grid: Shape-Based Matching` — it is the one piece of Grid-specific knowledge that LLD consumes, kept as a plain tuple of strings rather than exposing any richer Grid type, matching the existing boundary discipline ("Grid-specific behavior ends at normalization," `docs/high-level-design.md § Approach`). `control_module` is read by `docs/llds/app-ui.md`'s module-tier Control Grouping — recovering, for UI display only, information `address_table`'s existing `dict[_Key, _Key]` shape (§6) deliberately discards for event-resolution purposes; this is a second, independent lookup built alongside `address_table` from the same walk, not a change to `address_table` itself or to how an incoming MIDI event resolves. Both fields are populated for every `Ready` outcome and are simply absent in spirit (empty tuple / empty mapping) for a topology with zero recognized modules — which cannot actually occur, since zero recognized modules can still settle but would make `bank_count == 0` and an empty logical-control set, already a pre-existing, harmless edge case this addition does not change.

## 5. Active Grid Controller

**The problem this section solves**: `MappingEngine`, `preset_store.load_group_axis_targets()`, `mapping_view_model.py`'s row builders, and `MidiInputAdapter` all currently take or read a `ControllerProfile` — a concrete, frozen dataclass whose fields are populated once from a YAML file at load time. Grid has no YAML file and no load time in that sense — its shape is whatever `GridTopology` says *right now*. Manufacturing a `ControllerProfile` via `build_profile()` to paper over this would be an honesty problem in the codebase (a `ControllerProfile` means "a fixed fact about one device declared in a file," which Grid's shape isn't), not just an engineering shortcut — so this LLD does not do that.

**The resolution: a structural `ActiveController` shape, not a shared base class.** `MappingEngine`/`preset_store`/`mapping_view_model`/`MidiInputAdapter` each already read only a *subset* of `ControllerProfile`'s fields; `ControllerProfile` already happens to satisfy that subset's shape today, with zero changes required to it. A `typing.Protocol` naming that subset lets a second, independent class satisfy the same shape without either class knowing about the other.

**Corrected Protocol, reviewed against every actual call site (this revision adds two members missed in the previous draft — `has_native_mode` and `matches()`, both read by `MidiInputAdapter`, a consumer the previous draft underweighted):**

```text
class ActiveController(Protocol):
    name: str
    default_channel: int
    has_native_mode: bool
    has_jog_wheel: bool
    has_scene_button: bool
    bank_count: int
    bank_fader_keys: tuple[_Key, ...]
    fader_keys: frozenset[_Key]
    knob_to_fader: Mapping[_Key, _Key]
    mute_to_fader: Mapping[_Key, _Key]
    fader_to_knob: Mapping[_Key, _Key]
    opinionated_map: Mapping[_Key, _MapEntry]
    control_names: Mapping[_Key, str]
    websocket_keys: WebSocketKeys | None
    group_keys: GroupKeys | None
    def bank_fader_key(self, key: _Key) -> _Key | None: ...
    def matches(self, port_name: str) -> bool: ...
```

Every member above was checked against an actual read site: `MappingEngine.process()`/`process_websocket()`/`process_keystroke()` read `default_channel`, `has_jog_wheel`, `has_scene_button`, `fader_keys`, `bank_fader_key()`, `opinionated_map`, `websocket_keys`, `group_keys`, `fader_to_knob`, `bank_fader_keys`; `mapping_view_model.py`'s row builders read `bank_fader_keys`, `control_names`, `knob_to_fader`, `mute_to_fader`, `fader_keys`, `bank_fader_key()`, `opinionated_map`, `has_jog_wheel`; `MidiInputAdapter` reads `has_native_mode` and `matches()`. `setup_hint` is deliberately **not** in this Protocol — it's read only by `app.py`'s UI wiring, not by any of the four consumers above, and stays an `app.py`-level concern (see Open Questions). `ControllerProfile` satisfies this Protocol today, unmodified.

**`bank_count` is not the same thing as a module's full logical-control count — keep these separate, by name, everywhere:**

```text
bank_count            = the number of normalized PBF4 faders only
                         (the only elements that participate in Bank/Group axis control)
logical_control_count = every stable logical identity Grid exposes
                         (faders + pots + buttons + VSN1 buttons/jog)
```

For `PBF4 | VSN1 | PBF4`: `bank_count = 8`, while the full logical-control set also includes 8 PBF4 pots, 8 PBF4 buttons, 12 VSN1 buttons, and 1 VSN1 jog — none of which are Banks.

**`GridRuntimeController`** (a plain class, not a frozen dataclass — its fields are derived from a live `GridTopology`, not fixed at construction) is built as follows, returning a `GridControllerBuildOutcome` rather than assuming success:

```text
GridControllerBuildOutcome =
    Ready(controller: GridRuntimeController)
  | UnsupportedTopology(reason: str)   # multi-row (§3) only, as of Phase 1.3 — see step 2 below
  | AddressCollision(details: ...)     # two controls share a raw address (§6)
```

1. Validate the settled `GridTopology` is a single row (§3's rule, over *every* detected module). On failure: `UnsupportedTopology`.
2. **(Phase 1.3: no longer a validation step.)** A topology may now contain any number of recognized VSN1 modules — step 4 below numbers all of them globally, so there is no longer a logical-identity-collision risk to reject in advance. (Historical note: Phase 1 rejected a second VSN1 here, via `UnsupportedTopology`, because the old singular `("grid_vsn1_button", N)`/`("grid_vsn1_jog", None)` identity scheme would have let a second VSN1 alias the first's keys; `§4`'s revised global numbering removes that aliasing risk at the source, so this step is removed rather than kept-but-relaxed.)
3. Normalize into left-to-right module order (`normalize_linear_order()`, §3).
4. Walk the ordered modules' elements per their `GridModuleDefinition` (recognized modules only), assigning each `role="fader"` element the next `grid_fader` logical index, and independently numbering PBF4's `potentiometer`/`button` roles and VSN1's `button`/`endless` roles the same way (§4's revised normalization rule) — VSN1's button sequence continues globally across every recognized VSN1 module rather than resetting per module, and each VSN1 module's jog/jog-button is additionally tagged with that module's 1-based VSN1-instance ordinal (§4). This same walk also populates `module_shape`/`control_module` (§4's Phase 1.3 addition).
5. Build `address_table` (§6) from the ordered elements' *raw* `x`/`y` and the settled `current_page`. On any duplicate `(channel, type, number)` key: `AddressCollision` — construction stops, nothing partial is returned.
6. Reuse the *existing*, profile-agnostic entry-builder helpers already in `mapping.py` (`build_bank_membership()`, `build_control_names()`) by handing them a synthetic `ControlsConfig`-shaped input whose "CC numbers" are actually the stable logical indices from step 4. **Decided this revision (previously left open): parameterize, don't duplicate.** `_fader_entries()`/`_knob_entries()`/`_mute_entries()` hardcode the key tag `"cc"` today; Phase 2 implementation adds a `key_type: str = "cc"` parameter to each (default preserves every existing Korg call site byte-for-byte) so the exact same Bank-pairing/encoder-offset arithmetic produces `("grid_fader", N)`-tagged entries for Grid, with zero duplication of that arithmetic. The alternative (Grid duplicating equivalent helpers) was rejected: the formula is already profile-agnostic, and duplicating it risks the two copies drifting apart under a future `static-mapping.md` change.
7. `opinionated_map` is populated for `grid_fader` entries only (`/dragonframe/encoder/{N}`, the same default a Korg fader gets) — PBF4 pots/buttons and VSN1 buttons/jog get a `control_names` entry (nameable/visible) but no `opinionated_map` entry yet (§19's "identity now, default action later").
8. `default_channel = topology.current_page % 16` — **not a hardcoded `0`.** Since Phase 1's single-row rule forces every module's `y = 0`, the formula (§6) collapses `moduleY * 4` to `0`, leaving `channel = currentPage % 16` — whatever page is actually active, read from the gridmaster's heartbeat (§2, §3), not assumed. In the overwhelmingly common case (a chain never taken into a non-default page) this is `0`, but it is *derived*, not baked in — see Decisions & Alternatives for why this is a meaningful correction over the previous draft.
9. `has_native_mode = False`, `has_jog_wheel = False`, `has_scene_button = False`. **`has_jog_wheel`'s `False` is a deliberate, code-verified decision, not an oversight** — see the callout below.

**Why `has_jog_wheel = False`, and how VSN1's jog enters the pipeline instead (resolved from code, not guessed).** `has_jog_wheel` does not mean "this controller has some kind of jog/endless input" generically. Reading `mapping.py` directly: it gates two *specific*, hardcoded-Korg behaviors — `process()` dispatches a fixed key, `_JOG_WHEEL_KEY = ("cc", 110)`, through `_process_jog()`, which decodes the KORG-specific sign-magnitude relative encoding (`1–63` clockwise, `65–127` counterclockwise); and `process_keystroke()` additionally synthesizes the Arc Motion Control "Step Moco Forward/Back" keystroke for the same fixed CC. Both are Korg wire-format and Korg-action specifics that have nothing to do with VSN1's endless encoder, which (a) is not addressed at a fixed CC110 — its address is topology-derived like everything else on Grid — and (b) has no established Dragonframe action to synthesize in Phase 1 (§19). Setting `has_jog_wheel = True` for Grid would be actively wrong: it would make `MappingEngine` try to KORG-decode whatever happens to land on CC110 under Grid's own addressing, which is not what VSN1's jog sends. VSN1's jog instead gets its own ordinary logical identity, `("grid_vsn1_jog", None)` (§7), resolved through the same `address_table` path every other Grid control uses — with no `opinionated_map` entry yet, exactly like PBF4's pots/buttons.

**Implemented.** `dragonmidi/active_controller.py` defines the `ActiveController` Protocol exactly as above (`@runtime_checkable`, confirmed by `isinstance()` conformance tests against both `ControllerProfile` and `GridRuntimeController`); `dragonmidi/grid_controller.py` builds `GridRuntimeController`. `MappingEngine.__init__`/`set_profile()`/`profile` and `MidiInputAdapter.__init__`/`set_profile()`/`profile` are retyped to `ActiveController` (`dragonmidi/mapping.py`, `dragonmidi/midi_input.py`) — a pure type-hint change, zero behavior change, confirmed by the full existing regression suite passing unchanged. **Two implementation-level deviations from this section's exact wording, both documented in the completion report:** (1) only `_fader_entries()`/`build_bank_membership()` were parameterized with `key_type`, not `_knob_entries()`/`_mute_entries()` — Grid Phase 1 never populates knobs/mutes, so parameterizing those two would be speculative, untested generalization; (2) `control_names` for PBF4 pots/buttons/VSN1 buttons/jog is built by `grid_controller.py`'s own small naming logic, not by reusing `build_control_names()` — Grid's display names ("Grid Fader 3," "VSN1 Button 7") are genuinely different text from Korg's ("Fader Channel 3"), so there was nothing to usefully share beyond the already-reused Bank-pairing arithmetic.

## 6. MIDI → Module/Element Resolution

**The formula** (source: `grid-fw/common/src/lua/simplemidi.lua`, cross-confirmed against Intech's own docs — see `docs/high-level-design.md § References`):

```text
channel           = (moduleY * 4 + currentPage) % 16
cc_or_note_number = (32 + moduleX * 16 + elementIndex) % 128
command            = Note On          if the element's role is "button"
                      Control Change   otherwise
```

**`moduleX`/`moduleY` here are always the module's *absolute*, un-normalized topology coordinates — never the normalized left-to-right rank (§3).** This is Grid's own firmware-side formula, computed before DragonMIDI ever sees the data; DragonMIDI only *inverts* it, using the exact inputs the firmware used. Feeding it a normalized rank instead of raw `x` would silently miscompute every address. **`currentPage` is the value read from the gridmaster's heartbeat (§2, §3), not an assumed constant** — see §5, step 7 for why `default_channel` is therefore `currentPage % 16`, not a hardcoded `0`.

**Resolution is a precomputed reverse lookup, not a per-event formula inversion.** Whenever a `GridTopology` settles and `GridRuntimeController` is (re)built, it also builds:

```text
address_table: dict[_Key, (GridModule, GridElement)]
```

by running the *forward* formula once per element of every recognized module currently in the (validated, single-row) topology: for element `e` of module `m`, `key = ("note" if e.role == "button" else "cc", (32 + m.x * 16 + e.index) % 128)` on channel `currentPage % 16`. Per-event resolution is then a single dict lookup against this table — the same O(1) dispatch shape `MappingEngine.process()`'s own `opinionated_map` lookup already is.

**Implementation deviation, documented here:** `grid_controller.py`'s actual `address_table` is `dict[_Key, _Key]` — raw key straight to the resolved *logical* key — not `dict[_Key, (GridModule, GridElement)]`. Nothing in Phase 1 ever needs to recover which physical module/element a raw event came from after resolution (only the logical identity matters downstream), so the simpler shape is sufficient and is what `resolve_grid_event()` (§7) looks up directly.

**The acceptance criterion is address uniqueness, not a hardcoded module-count ceiling.** Because the number wraps modulo 128 and each `x` position occupies a 16-wide block (`elementIndex` only ever needs 0–13), the same raw block repeats every `128 / 16 = 8` positions of `x` — two modules whose `x` values are congruent mod 8 will produce overlapping, likely colliding, addresses (both module definitions use overlapping low element indices, so a collision is the expected outcome of this situation, not a rare coincidence). This is why, for example, `1 × PBF4` (4 faders), `PBF4 | VSN1 | PBF4` (8 faders + VSN1's controls), and `PBF4 | PBF4 | PBF4` (12 faders) all work — and why `8 × PBF4` (32 faders) is *also* expected to work, since 8 consecutive `x` positions tile the 128-value space exactly once with no overlap — while a 9th adjacent PBF4 would not. **DragonMIDI does not hardcode this "8 modules" number as a rule** — it validates the *actual* resulting `address_table` for duplicate keys on every build, which is what actually matters; the mod-8 arithmetic above is only an explanation of why a sufficiently wide row can fail, not a separate limit enforced on its own.

**Collisions fail controller construction closed — this reverses the previous draft's "last one wins."** If building `address_table` would assign the same `(channel, type, number)` key to two different elements, `GridRuntimeController` construction returns `AddressCollision` (§5) and no Grid controller becomes active. Silently dropping or overwriting one of the two colliding controls would mean DragonMIDI accepts input it cannot correctly attribute, which is exactly the "don't guess" principle this whole revision is about — unlike the Korg "duplicate matching port, take the first" precedent (two *interchangeable* physical units), a collision here means two *specific, non-interchangeable* logical controls cannot both be reached, and there is no safe default choice between them.

**Negative `x` is handled correctly by construction**, not as a special case: Python's `%` operator already returns a non-negative result for a positive modulus regardless of the dividend's sign, so a module to the left of the USB root (negative absolute `x`) produces the same well-formed address space as a positive one — no separate negative-`x` branch is needed in the formula itself.

**Unsupported modules within an already-confirmed single row don't threaten uniqueness.** Since an unrecognized module contributes no elements to `address_table` at all (§3, §4), it cannot itself cause or hide a collision — only recognized modules' elements are ever checked against each other.

**No topology, no interpretation.** Before a `GridTopology` has settled at least once, `address_table` does not exist, and *every* raw Grid MIDI event resolves to nothing — DragonMIDI never guesses a module/element from an incomplete or absent topology. This is the same "fail closed, not loud" posture `normalize_raw()` already takes toward unrecognized MIDI message types.

**Factory defaults only, now correctly scoped around the real page value.** This formula describes Grid's *default* ("MIDI Auto") addressing, using whichever page is actually active (§5). A module whose MIDI Auto settings have been individually edited in Grid Editor, or that has a custom Package loaded, no longer matches this formula regardless of page — out of scope (Non-Goals) and not detected; such a module's events simply fail to resolve (same "no match in `address_table`" outcome as any other unmatched event), rather than DragonMIDI misinterpreting them as a different control.

## 7. Logical Control Identity

Grid's logical controls are expressed as ordinary `_Key` tuples (`mapping.py`'s existing `tuple[str, int | None]`) — **the same type `MappingEngine.process()` already dispatches on**, with Grid-specific type tags whose second element is a **stable logical index**, never a raw CC/note number:

```text
("grid_fader", N)         # N = 1..bank_count, left-to-right across all PBF4 modules
("grid_pbf4_pot", N)       # left-to-right across all PBF4 modules, independent of fader numbering
("grid_pbf4_button", N)    # left-to-right across all PBF4 modules
("grid_vsn1_button", N)    # N = 1..12, by VSN1's own element-index order (0-7, then 9-12)
("grid_vsn1_jog", None)
("grid_vsn1_jog_button", None)   # confirmed 2026-11-04: the encoder's own push-button, same raw index, see §4
```

**VSN1 jog, characterized against real hardware (2026-11-04 validation) — confirmed absolute and bounded, not Korg-relative.** The factory ("MIDI Auto") jog sends plain `CC` values that climb and fall smoothly across the full `0`–`127` range as it turns, clamping (not wrapping) at both ends — observed turning past the low end producing a long run of repeated `0` values rather than rolling over toward `127`. This is neither the Korg-style fixed-CC110 sign-magnitude relative encoding `has_jog_wheel`/`_process_jog()` decode (§5's "why `has_jog_wheel = False`" already correctly avoids applying that decode to Grid) nor a truly unbounded "endless" wire value despite the encoder's name. **No code change follows from this**: Phase 1's design already passes the jog's `raw_value` through completely undecoded, tagged only with the stable `("grid_vsn1_jog", None)` identity (above) — the right representation regardless of whether the real encoding turned out absolute, relative, or something else, since Phase 1 assigns the jog no `opinionated_map` entry and interprets none of its semantics. A future phase building a Grid jog action now knows what it is actually working with: a bounded absolute position, not a per-tick relative delta.

**Reviewed whether the `grid_` prefix is actually necessary (this revision): it is kept, on consistency grounds, not naming purity.** Korg's own engine-dispatch keys are never semantic role names at all — they're always a raw-address pair, `("cc", N)`/`("note", N)`, with no `"fader"`-type tag anywhere in that space; the only places this codebase *does* use descriptive, non-raw-address key tags are view-model-only synthetic rows (`"knob_summary"`, `"mute_summary"`, `"solo_websocket"`, `"jog_wheel_keystroke"` in `mapping_view_model.py`) — every one of them a compound, descriptive name, never a bare single word. A bare `("fader", N)` would be the one new key that's both semantic *and* terse, matching neither convention already in the codebase; `grid_`-prefixed compound names match the second. No refactor is needed either way — this is a new key space, not a rename of anything existing — so the choice costs nothing to make either way, and this revision keeps the previous draft's choice, now with a concrete reason rather than a stylistic preference.

**How a raw Grid MIDI event becomes one of these**: the Grid normalizer (part of `GridRuntimeController`) takes the already-normalized `MidiEvent` that `midi_input.py`'s existing `normalize_raw()` produced from the real `mido` message (unchanged — Grid's wire format is ordinary CC/Note, nothing about *that* step is Grid-specific), looks up `(event.type, event.number)` in `address_table` (§6) **only if the controller is currently valid (not stale, §10)**, and if found, returns a **new** `MidiEvent` with `type`/`number` *rewritten* to the resolved logical key's tag/index while `channel`, `raw_value`, `normalized`, `is_press`, `is_release` pass through unchanged. **This rewritten event is handed to `MappingEngine.process()` completely unchanged from how any other controller's event reaches it** — this is the entire "Grid-specific behavior ends at normalization" claim the HLD makes, made concrete: there is no second code path into the Mapping Engine, only a different *source* for the same `MidiEvent` shape.

**Raw CC/note numbers are never a logical control's permanent identity.** `address_table` is rebuilt from scratch every time topology (re)settles; the same `("grid_fader", 3)` key can point at a different raw `(channel, type, number)` triple before and after a rearrangement, while remaining the exact same key the Mapping Engine, Preset Store, and Mapping View all see.

## 8. Controller-Defined `bank_count` and MIDI-Port Discovery

`bank_count` reaches every consumer that already reads it from `ControllerProfile.bank_count` through the `ActiveController` Protocol (§5) — none of those call sites need a Grid-specific branch; they need only be retyped (Phase 2, not this task) from the concrete `ControllerProfile` to the structural `ActiveController`. `GridRuntimeController.bank_count` is `len(bank_fader_keys)`, computed fresh every time topology settles — the identical derivation `ControllerProfile.bank_count` already uses, just fed from a different source.

**`app.py`'s MIDI-side discovery needs no new mechanism, only a shared helper.** Today `MidiInputAdapter` calls `profile.matches(port_name)`, which fuzzy-normalizes (strip non-alphanumeric, lowercase) and checks for a substring — implemented today as a module-level `_normalize()` function in `controller_profile.py`, called from `ControllerProfile.matches()`. Source research had assumed Grid's MIDI interface would expose its own confirmed USB descriptor string (`grid-fw/common/src/c/grid_usb.c`'s `s_str_table`): `"Intech Grid MIDI"`, distinct from the device's bare product string (`"Grid"`) and the CDC interface's own string (`"Intech Grid CDC"`, §1) — giving `match_substring = "intechgridmidi"`. **Corrected against real hardware (2026-11-04):** a real Grid's CoreMIDI port name (confirmed via `mido`) is simply `"Grid"` — the bare product string, not a distinct per-interface descriptor. `"intechgridmidi"` can never be a substring of the shorter `"grid"`, so MIDI auto-connect would never have fired; `match_substring` is now `"grid"`, which still also matches the originally-assumed fuller name, so it is strictly more permissive rather than narrower. **Rather than have `GridRuntimeController` depend on `controller_profile.py` for this** (an unnecessary coupling to a module whose whole purpose is YAML-declared profiles), Phase 2 implementation extracts the existing normalization into a small standalone helper — e.g. `dragonmidi/name_matching.py`'s `fuzzy_contains(match_substring: str, name: str) -> bool` — that `ControllerProfile.matches()` is refactored to call, and that `GridRuntimeController.matches()` calls independently. Both end up with identical matching behavior; neither depends on the other's module. With that in place, `MidiInputAdapter`'s *existing* `poll_discovery()`/`connect()` path opens Grid's MIDI port exactly the way it opens any other controller's — no new discovery mechanism for the MIDI side at all. Only the CDC/topology side (§1) needs an independent discovery mechanism, since Korg controllers have no analog to it.

## 9. Initialization Lifecycle

1. User selects "Intech Grid" from the Controller Profile dropdown.
2. Grid CDC Transport (§1) begins polling for VID/PID-matching serial ports. If more than one candidate is found, the sequence stops here with an ambiguous-chains status (§1, §11) — Grid does not proceed to step 3 until exactly one candidate exists.
3. On a single match, opens it at 2,000,000 baud. Raw bytes stream into the Grid Frame Parser (§2); recognized `heartbeat_type` `0`/`1` heartbeats (and the gridmaster's piggybacked `PAGEACTIVE`) feed the `GridTopologyBuilder` (§3); `heartbeat_type == 255` (editor) is recognized and discarded.
4. The builder waits for its settle condition: no structural change (§3's definition) for the settle window, **and** at least one gridmaster heartbeat seen. Before this point, the UI shows the same "Waiting for …" state `midi-input.md` already defines for any controller with no connected device yet.
5. Once settled: `GridRuntimeController` construction runs (§5's numbered steps) against the full detected module set. A `GridControllerBuildOutcome` other than `Ready` (`UnsupportedTopology` or `AddressCollision`) stops the sequence here — no controller becomes active, and the status (§11) reflects which failure occurred.
5a. **(Phase 1.3.)** On `Ready`, before anything is installed: `resolve_grid_named_controller()` (`docs/llds/named-controller.md § 3`) runs against the new controller's `module_shape`. An `Activated` outcome continues to step 6 using that outcome's Named Controller `id` as the Preset Store key in step 8 below. An `Ambiguous` outcome stops the sequence here exactly as `UnsupportedTopology`/`AddressCollision` do — no controller becomes active, the Grid runtime controller that was just built is held but not installed, and the status (§11) reflects a new "ambiguous named controller" state until the ambiguity dialog (`docs/llds/app-ui.md`) resolves it, at which point the sequence resumes at step 6 using the user's chosen (or newly-created) Named Controller's `id`.
6. Once a Named Controller `id` is settled (step 5a): `app.py`'s composition root hands the `GridRuntimeController` to `MappingEngine` and to the Mapping View/Configuration Dialog's row builders — the exact same wiring call sites already use for a freshly-selected `ControllerProfile`, since both satisfy the same shape.
7. The ordinary `MidiInputAdapter`/MIDI backend opens Grid's USB-MIDI port (by the confirmed `match_substring`, §8) and begins delivering raw events; each passes through the Grid normalizer (§7, resolving against `address_table`) before reaching `MappingEngine.process()` — from here, event handling is indistinguishable from any other controller's, **provided the controller is still valid** (§10).
8. The Preset Store loads the active Named Controller's `id`-keyed persisted (Bank, Group) table (§12), bounded by this session's `bank_count`, exactly as it does for any profile switch.
9. From this point, the Grid CDC Transport continues delivering heartbeats, and the topology builder continues watching for a structural change against the settled snapshot — see §10.

## 10. Topology Change Policy: Fail Closed, Not Stale-but-Serving

**Corrected policy (this revision).** The previous draft left a running session's `address_table` in place indefinitely after a structural change, reasoning that "nothing incorporates the change, so nothing breaks." That's not good enough: an `address_table` built from a topology that no longer matches reality can actively **misattribute** incoming MIDI to the wrong logical control (e.g. a module physically removed and a different one reconnected at the same `(x, y)` with a different `hwcfg`) rather than merely failing to reflect a harmless addition. **The corrected policy is fail-closed, not merely non-live:**

- The `GridTopologyBuilder` keeps watching for a structural change (§3's precise definition) for as long as a `GridRuntimeController` built from its last settled snapshot is active — not only during the initial settle window.
- **The instant a structural change is detected, the active `GridRuntimeController` is marked `STALE`.** A `STALE` controller's Grid normalizer (§7) stops resolving *any* incoming Grid MIDI event — every event produces nothing, the same "no topology, no interpretation" outcome §6 already defines for the pre-settle case, now also covering the post-settle case where a stale interpretation would otherwise be actively wrong rather than merely absent.
- **No live rebuild.** Marking `STALE` does not trigger a fresh settle/rebuild on its own — Phase 1 does not attempt to keep the Mapping View, Bank/Group assignments, or `address_table` correct against a moving target mid-session.
- **Recovery, as of Phase 1.5.2: an "Intech Grid modules changed - refresh now?" prompt, shown once per STALE episode** (`app.py`'s `_prompt_grid_topology_changed()`, `@spec GRID-APP-006`), the instant the controller goes `STALE` — not only on the next status-line glance. OK forces the same fresh discovery/settle cycle reselecting "Intech Grid" from the dropdown already performed (`_refresh_grid_connection()`, shared by both paths); Cancel dismisses the prompt and leaves the controller `STALE` exactly as before this phase — manually reselecting "Intech Grid" from the dropdown remains the fallback recovery path, unchanged, for a dismissed or missed prompt. The prompt does not re-show on every tick while STALE persists unanswered (a one-shot flag, reset only by the next successful refresh); it is a blocking dialog, the UI timer stopped around it exactly like the Ambiguous Named Controller dialog (§14) already does, for the same re-entrancy reason. **This changes only how recovery is surfaced, not the underlying policy**: a structural change still marks the controller `STALE` immediately and stops it resolving Grid MIDI the same tick (no live rebuild, no partial reinterpretation) — see the table below, unchanged.

| Event | §3's classification | Phase 1 behavior |
|---|---|---|
| Module added while running | Structural change (new slot) | Marked `STALE` immediately; Grid MIDI stops resolving until reselect |
| Module removed while running | Structural change (slot times out) | Marked `STALE` immediately; Grid MIDI stops resolving until reselect |
| Module reordered / USB root moved | Structural change (coordinates shift) | Marked `STALE` immediately; Grid MIDI stops resolving until reselect |
| Module's `hwcfg` changes at an unchanged coordinate | Structural change | Marked `STALE` immediately; Grid MIDI stops resolving until reselect |
| Active page changes | Structural change (§3) | Marked `STALE` immediately; Grid MIDI stops resolving until reselect — the built `address_table`'s channel assumption no longer holds |
| Repeated, unchanged heartbeat from an already-known module | Ordinary refresh | No effect; the controller remains valid |

## 11. UI Implications (No Redesign)

- "Intech Grid" is one more entry in the existing Controller Profile dropdown (`docs/llds/app-ui.md`) — no new dropdown, no per-module sub-selection.
- The Mapping View's fader-row count already derives from `profile.bank_fader_keys` (confirmed generic during the `bank_count` refactor that preceded this LLD) — Grid's `bank_count` flows through unchanged; a PBF4-only chain shows 4 rows, a `PBF4 | VSN1 | PBF4` chain shows 8, with no Mapping View code change.
- **No live rebuild guarantee while already active**: the Mapping View does not promise to reflect a structural change that happens while Grid is already the active, connected controller — a `STALE` Grid controller (§10) leaves the Mapping View showing its last-built row set, now driving nothing, until a reselect. This is distinct from a *deliberate* controller switch (a different static profile, or a freshly-settled Grid topology after reselecting), which does rebuild correctly — `app-ui.md`'s formerly-documented "Mapping View is build-once, refresh-content-only" gap was closed as part of this task's application integration (§14) specifically because Grid's variable `bank_count` made it load-bearing; what remains out of scope is only a live rebuild against an already-active session's moving target, which Phase 1 handles by going `STALE` instead (§10), not by silently continuing to show wrong rows.
- Group switching (Track ◄/►, 5 Groups) operates on Grid's `bank_count` exactly as it does for any profile — no Grid-specific Group code. **Accepted Phase-1 limitation**: neither PBF4 nor VSN1 has an element wired to Group switching (`group_keys = GroupKeys(previous=None, next=None)`), so a Grid session is effectively pinned to Group 1 until a future phase wires a control to it.
- **Status model: six distinguishable states as of Phase 1.3 (five through Phase 1.2), zero new indicator widgets.** The task calls for a user to be able to tell apart *Grid active*, *Grid initializing*, *Grid unsupported*, *Grid stale/reselect required*, *Grid ambiguous/collision*, and — new in Phase 1.3 — *Grid settled but its Named Controller is ambiguous*, without a log pane or a UI redesign. Mapped onto the Status UI's **existing** vocabulary (`docs/llds/app-ui.md`'s 3-state indicator dot plus its free-text connection-status line, the same slot that already renders "Waiting for nanoKONTROL Studio…" or a connected device's name):

  | Required state | Existing mechanism reused |
  |---|---|
  | Grid initializing | The existing "quiet"/"Waiting for Intech Grid…" state — no change. |
  | Grid active | The existing "live" state plus the active Named Controller's `display_name` (Phase 1.3: previously the bare device-name text) — see `docs/llds/named-controller.md`. |
  | Grid unsupported (multi-row topology) | The existing *error* dot state, with the connection-status text line carrying a short distinguishing phrase (e.g. "Intech Grid: unsupported topology") — the same text slot, just richer content. |
  | Grid stale / reselect required | The existing *error* dot state, text line reading e.g. "Intech Grid: topology changed — reselect to apply." |
  | Grid ambiguous / collision | The existing *error* dot state, text line distinguishing "multiple Grid chains found" from "address collision," using the same slot. |
  | Grid named-controller ambiguous (Phase 1.3) | The existing *error* dot state, text line reading e.g. "Intech Grid: multiple saved configurations match — choose one," pending resolution of the ambiguity dialog (`docs/llds/app-ui.md`, `docs/llds/named-controller.md § 3` step 5). Distinct from the "ambiguous / collision" row above, which is a hardware-discovery ambiguity (multiple Grid CDC candidates, or an address collision) and not a saved-identity ambiguity — the two must not share wording, per `docs/llds/named-controller.md § Open Questions` item 3. |

  This needs no new widget — only (a) the connection-status text line accepting Grid-authored content beyond a bare device name (already free text today, just not yet asked to say this much) and (b) the *error* dot being repurposed, the same way it already carries a different concrete meaning per profile today (Native Mode failure for the Studio vs. OSC listener-bind failure elsewhere). **Resolved in Application Integration (§14)**: the text source is dynamic, not per-profile-static — `grid_status_text(status, unsupported_reason)` is recomputed every UI tick from `GridAppCoordinator`'s live state and passed as `status_presenter`'s `midi_status_override`; the exact wording for each state is `grid_status_text()`'s own `_STATUS_TEXT` table (`dragonmidi/grid_lifecycle.py`).

## 12. Persistence

**No Preset Store schema or code change is required.** `preset_store.py` already persists the (Bank, Group) axis-assignment table keyed by **a controller identity string + positional Bank index + Group index** — never by raw CC (confirmed during the `bank_count` refactor, which also made the load path's Bank-index ceiling a caller-supplied `bank_count` rather than a hardcoded `8`). Both of this task's stated goals fall out of that existing design for free:

- **Survives a USB-root change or module rearrangement** that preserves the same `bank_count` (not the same `logical_control_count`, §5 — only `grid_fader` Banks are persisted at all): Bank N already means "the Nth `grid_fader`, left-to-right," which is exactly the quantity normalization keeps stable.
- **A missing logical control** (the saved table has an entry for a Bank index beyond the currently-connected chain's `bank_count`) is already handled: `load_group_axis_targets()`'s existing bounds check against the caller-supplied `bank_count` skips any out-of-range entry with a logged warning, exactly as it already does for a hand-edited or stale file today. No Grid-specific handling needed.

**Keying, revised Phase 1.3: the Named Controller's `id`, not the bare constant `"Intech Grid"`.** Through Phase 1.2, `GridRuntimeController`'s profile-name-equivalent used to key its preset file was required to be the fixed constant `"Intech Grid"` — correct as far as it went, but exactly the gap `docs/high-level-design.md`'s Named Controller Registry paragraph and `docs/llds/named-controller.md` exist to close: every physically-distinct rig sharing one module-type shape collided on that one constant. As of Phase 1.3, `app.py`'s composition root resolves a Named Controller (`docs/llds/named-controller.md § 3. Grid: Shape-Based Matching`) from the settled controller's `module_shape` (this LLD's own new field, § Module Definitions) *before* calling `preset_store.load_group_axis_targets()`/`save_group_axis_targets()`, and passes that Named Controller's `id` as the key — never `GridRuntimeController.name` directly. `GRID_PROFILE_NAME`/`GridRuntimeController.name` remain `"Intech Grid"` (the Status UI's display label, `GRID-APP-001`'s dropdown entry text — unrelated to the Preset Store key now). This is still "a constant, never topology-derived" in the sense the original requirement cared about — keying on anything topology-dependent would still silently fragment one chain's saved mappings across multiple files as it's rearranged — it is just no longer *the same* constant for every physical rig; the Named Controller's `id`, once assigned at creation (`docs/llds/named-controller.md § 3`), is itself exactly such a constant for the rig it was created for.

**Accepted, matches existing precedent**: if a rearrangement changes *which physical fader* is "3rd from the left" while keeping the same total count and the same module-type shape, the persisted Bank-3 assignment now applies to a different physical fader than before. Not a new gap — Bank N has always meant "the Nth positional slot," never "this exact physical control," for the Korg profiles too (`MAP-CONFIG-008`), and this LLD's `module_shape`-based Named Controller matching (`docs/llds/named-controller.md`) does not attempt to detect this particular rearrangement either (its own Non-Goals, § 8).

**Nothing new to persist for PBF4 pots/buttons or VSN1 buttons/jog in Phase 1** — they have no `opinionated_map` entry and no Mapping View row yet (§5, §11, §19), so there is no user-editable target for them to lose or need to persist.

## 13. Licensing / Provenance

DragonMIDI is GPL-3.0-or-later. `grid-protocol`, `grid-editor`, and `grid-fw` are **GPL-3.0-only** (plain FSF template, no "or later" grant, no SPDX markers — confirmed by direct inspection of all three repos' `LICENSE` files).

**What this LLD describes is fact-level reimplementation, not code adaptation**: the HWCFG table, the element index tables, the frame field offsets, the heartbeat `TYPE`/`PAGEACTIVE` semantics, and the MIDI Auto addressing formula are *protocol facts* — observable, documented behavior of the hardware/firmware — reimplemented independently in original Python from those facts, not ported from Intech's C, TypeScript, or Lua source. No source lines from any of the three repositories are copied into this LLD or are intended to be copied into DragonMIDI's implementation.

**Why this matters for licensing**: a clean-room reimplementation of a documented fact (a lookup table of integers, a two-line arithmetic formula, a byte-offset layout) does not carry Intech's copyright into DragonMIDI, so DragonMIDI's own GPL-3.0-or-later terms are unaffected. This is different from *directly adapting* Intech source — if a future implementation detail turns out to need that (not currently anticipated for anything in this LLD), the adapted file would need `SPDX-License-Identifier: GPL-3.0-only` and the combined distributed work would be constrained to GPL-3.0 terms (not "-or-later") for as long as that adaptation remains, per ordinary GPL combination rules.

**Attribution**: Phase 2 implementation should carry a short provenance comment at each fact-table/formula site citing the specific upstream repository and file the fact was confirmed against — the same treatment `docs/high-level-design.md § References` already gives this research at the HLD level, pushed down to the code that actually encodes each fact.

## 14. Application Integration

**`GridAppCoordinator` (`dragonmidi/grid_lifecycle.py`) is the Qt-independent seam.** It wraps one `GridLifecycle` and exposes exactly the decisions `app.py`'s composition root needs, without touching a widget: `select_static()`/`select_grid()` (what a dropdown selection means), `poll()` (drives the lifecycle once per UI tick and returns the newly-ready `GridRuntimeController` exactly once, the instant it settles — `None` every other tick), `should_poll_midi_discovery()` (false only while Grid is selected but not yet settled), and `route_event()` (delegates to `route_midi_event()`, §6). Installing a ready controller into the Mapping Engine/MIDI Input Adapter and rebuilding the Mapping View/Configuration Dialog stays `app.py`'s own job — the coordinator only decides *when*.

**Controller-selection representation (`dragonmidi/controller_selection.py`).** The dropdown's items are `ControllerChoice = StaticChoice(profile: ControllerProfile) | GridChoice(name="Intech Grid")`, built by `build_controller_choices(profiles)` as `profiles + (GridChoice(),)`. `GridChoice` carries no `GridRuntimeController` — none exists until topology settles — only the stable display name. `app.py`'s `_on_profile_changed(index)` branches on `isinstance(choice, GridChoice)`: for `GridChoice`, calls `select_grid()` and `self._midi.disconnect()` and returns (no controller to install yet); for `StaticChoice`, calls `select_static()` (closes Grid's CDC connection if it was active; a no-op otherwise) and installs `choice.profile` via the same `_install_active_controller()` helper §9 step 6 and step 8 both route through — shared by the static-profile path and the Grid-ready transition, so there is exactly one place that calls `MappingEngine.set_profile()`, loads the Preset Store entry, calls `MidiInputAdapter.set_profile()`, and rebuilds (not refreshes) the Mapping View and Configuration Dialog.

**Status/error mapping reuses the existing indicator, exactly as §11 specified.** While `grid_active`, `_on_tick()` computes `grid_status_text(status, unsupported_reason)` and passes it as `compute_status_snapshot()`'s `midi_status_override` (added as an optional parameter to `status_presenter.midi_indicator()`/`compute_status_snapshot()`; every existing caller omits it, unaffected). The same tick calls `self._monitor.set_error("midi", grid_status_is_error(status))` — the existing `SignalMonitor` error flag, the same mechanism that already carries Native Mode failure for the Studio and OSC listener-bind failure elsewhere, now also carrying Grid's AMBIGUOUS/UNSUPPORTED/COLLISION/STALE. No new widget; `midi_indicator()`'s `status_override` wins over the connected/waiting-text logic whenever not `None`.

**MIDI dispatch gets exactly one new line, at the top of `_process_midi_event()`, before anything else:** `event = self._grid_coordinator.route_event(event); if event is None: return`. `route_event()` is a pass-through when Grid isn't active (the static-profile path is provably unaffected — the call is the identity function in that branch), and resolves-or-drops when it is (§6). Every output path below it (OSC, WebSocket, keystroke) is unchanged and unaware Grid exists.

**Discovery polling is blocked only during Grid's pending window.** `app.py`'s discovery `QTimer` now calls a small wrapper, `_on_discovery_tick()`, which calls `MidiInputAdapter.poll_discovery()` only when `should_poll_midi_discovery()` is true — false exactly while Grid is selected and `GridLifecycle.controller is None` (WAITING/AMBIGUOUS/INITIALIZING). This prevents two failure modes: polling trying to reconnect the just-disconnected previous static profile's device during the pending window, and polling racing Grid's own MIDI-port match before any Grid controller exists to match against. Once ACTIVE or STALE, discovery resumes normally — the MIDI port itself doesn't disappear when the controller goes stale, only event resolution does (§10).

**Thread safety correction (found while wiring, not previously specified): `GridLifecycle._on_bytes` no longer touches shared state directly.** `SerialGridTransport`'s real implementation reads on a background thread (`_SerialGridConnection._read_loop`) and invokes its callback from that thread — but `GridLifecycle.poll()` (driven from the Qt main thread's UI tick) was reading and mutating the same `GridFrameAccumulator`/`GridTopologyBuilder` state the callback wrote to, with no synchronization between them. Fixed the same way `MidiInputAdapter` already handles its own cross-thread callback: `_on_bytes` now only does `self._byte_queue.put(data)` (a thread-safe `queue.Queue`); `poll()` drains it (`queue_drain.drain_queue()`) as its first action, so `_accumulator`/`_builder` are only ever touched from the thread that calls `poll()`. `reinitialize()` also replaces the queue, so bytes still in flight from a just-closed connection can't bleed into the next cycle. Covered by `test_grid_lifecycle.py`'s `test_bytes_delivered_from_a_background_thread_are_processed_safely`, which delivers via an actual `threading.Thread` rather than the test's own thread.

**Shutdown.** `closeEvent()`'s existing `run_shutdown_sequence()` list gains `self._grid_coordinator.select_static` (closes Grid's CDC connection if it was active; a no-op otherwise) alongside the pre-existing `self._midi.disconnect`.

## Non-Goals (Phase 1)

Data Model`'s governing constraint applies equally here, since it is this LLD's own `module_shape`/`control_module` that Named Controller matching is built from).

## Decisions & Alternatives

| Decision | Chosen | Alternatives Considered | Rationale |
|---|---|---|---|
| Heartbeat `TYPE` inclusion | `TYPE 0` and `TYPE 1` both contribute modules to topology; every other value — `255` (editor) explicitly, and any value the protocol does not yet define — is excluded | Only `TYPE 1` counts as a discoverable module (previous draft); only the literal value `255` excluded (the revision immediately preceding this one, until the edge-case audit covered a hypothetical undefined `TYPE`) | Source-confirmed `(type=0 grid, type=1 gridmaster, type=255 editor)`; Grid Editor itself builds topology from the full set, and most real chains are mostly `TYPE 0` modules — excluding them would have discovered almost nothing. Generalizing the exclusion beyond the literal `255` closes a gap found during the edge-case audit (an undefined future `TYPE` value would otherwise have no defined handling) |
| Multiple recognized VSN1 modules (superseded Phase 1.3) | Number globally across all VSN1 modules (buttons) plus a VSN1-instance ordinal (jog/jog-button) — the same generalization PBF4 already had | *Phase 1 original*: reject Grid runtime-controller construction (`UnsupportedTopology`); leave unspecified; allow and let the second VSN1's elements overwrite the first's | Phase 1.3's task explicitly requires supporting repeated VSN1 modules. The original rejection existed only because the *old* singular identity scheme would have aliased a second VSN1's keys onto the first's — fixable at the root by generalizing the numbering scheme (as PBF4's already was) rather than a permanent restriction; safe to do outright since nothing is persisted under the old `None`-shaped jog key today |
| Current page | Read from the gridmaster's piggybacked `PAGEACTIVE` heartbeat frame; `default_channel = currentPage % 16` | Assume page 0 always, hardcode `default_channel = 0` | Source-confirmed the value rides along in data already being parsed, at no extra protocol cost — using it is strictly more correct than assuming it, and costs nothing extra to implement |
| Grid's "controller" shape | A structural `ActiveController` Protocol both `ControllerProfile` and `GridRuntimeController` satisfy | Fabricate a real `ControllerProfile` via `build_profile()`; add Grid-specific `if`-branches throughout `MappingEngine`/`preset_store` | Rules out fabricating a "fixed, file-declared" fact that Grid's shape isn't; avoids repeating the per-device-conditional mistake Controller Profiles were introduced to avoid |
| `ActiveController` Protocol membership | Reviewed against every real call site; added `has_native_mode`/`matches()` (read by `MidiInputAdapter`), excluded `setup_hint` (read only by `app.py`) | Ship the previous draft's Protocol unreviewed | A Protocol that's missing a genuinely-read member silently breaks at the one call site that needed it; one with speculative extra members invites drift from what's actually used |
| Logical control identity | `_Key`-shaped tuples with `grid_`-prefixed type tags and a stable logical index | A new `LogicalControl` dataclass; bare un-prefixed tags (`"fader"`) | `_Key` is already generic, letting Grid enter `MappingEngine.process()` with zero changes to it; `grid_`-prefixing matches this codebase's existing convention for non-raw-address dispatch/view keys, which bare tags would not |
| Entry-builder reuse | Parameterize `_fader_entries()`/`_knob_entries()`/`_mute_entries()`'s hardcoded `"cc"` key tag (default-preserving for Korg) | Duplicate equivalent builders inside a Grid-specific module | Avoids re-deriving the encoder-offset/Bank-pairing arithmetic a second time and the risk of the two copies drifting apart |
| Topology discovery channel | USB-CDC serial, opened directly by DragonMIDI (`pyserial`) | Require Grid Editor running; parse topology out of MIDI sysex | Source-confirmed no proprietary handshake exists; MIDI carries no topology data in Grid's default behavior at all |
| Module identity within a topology snapshot | `(x, y)` position | A stable per-module serial number | No serial number field exists in the heartbeat payload; position-as-identity suffices for "what's connected right now" |
| USB-root coordinate handling | Sort by absolute `x`, re-index by rank for *identity*; keep raw `x`/`y` for *address resolution* | Use rank for both; require a fixed USB-root end | Conflating rank and raw coordinate would make either normalization or address resolution wrong; a fixed-end requirement defeats the point of normalizing at all |
| Single-row (2-D) validation | **Reject the whole topology** if any detected module — recognized or not — reports a different `y` | Silently exclude the off-row module(s) and proceed with the rest (previous draft) | The user must never end up unknowingly controlling only a subset of an attached Grid; silent partial operation is exactly the failure mode this revision eliminates |
| Unsupported-module handling within a confirmed single row | Excluded from element enumeration, does not invalidate the row | Reject the whole row whenever any unsupported module is present | Once the row-validity check (above) has run over the *complete* module set, an unsupported module's absence from element enumeration cannot change the recognized modules' relative order — there is nothing left to be ambiguous about |
| Address-table collisions | **Reject `GridRuntimeController` construction entirely** (`AddressCollision`) | Log and let the second-built entry win (previous draft) | A collision means two non-interchangeable logical controls cannot both be reached; unlike a duplicate Korg port (two interchangeable units), there is no safe default choice between them |
| Topology-change handling mid-session | **Mark `STALE` immediately; stop resolving Grid MIDI until reselect** | Continue serving the last-built `address_table` indefinitely (previous draft); live incremental rebuild | Serving a stale table risks active misattribution, not just staleness; a live rebuild would have to solve mid-session UI/Bank-state invalidation for a capability Phase 1 doesn't require |
| Multiple Grid chains | Ambiguous — neither opened, explicit status surfaced | Connect to the first match (Korg's existing duplicate-port precedent) | Two Grid chains are not necessarily interchangeable the way two identical Korg units are; guessing which one risks silently driving the wrong rig |
| Status/error surfacing | Reuse the existing 3-state indicator dot plus its free-text connection-status line for all five required states | Add a new status widget or log pane | The task explicitly rules out a UI redesign; the existing text slot already renders arbitrary free text, and the error dot already carries different concrete meanings per profile |
| Preset Store schema | Unchanged — reuse as-is, keyed by a fixed `"Intech Grid"` name | Version the schema to record topology shape alongside the table | The existing positional-Bank-index design already satisfies both stated persistence goals |
| VSN1L/VSN1R | One shared `VSN1_DEFINITION` | Two distinct definitions with a shared base | Their element tables are identical; no behavioral difference to justify the distinction |
| `has_jog_wheel` for Grid | `False`; VSN1's jog enters the pipeline as `("grid_vsn1_jog", None)` through the ordinary `address_table` path | `True`, reusing the existing KORG sign-magnitude jog decode for VSN1's endless encoder | Verified from code: `has_jog_wheel` gates a fixed-CC110 KORG-specific decode and keystroke synthesis that has nothing to do with VSN1's topology-addressed, differently-encoded jog |
| Grid MIDI port discovery | Fuzzy-substring match against `"grid"` (corrected 2026-11-04 from the source-assumed, never-actually-observed `"Intech Grid MIDI"` — a real Grid's CoreMIDI port name is simply `"Grid"`), via a small shared helper neither `ControllerProfile` nor `GridRuntimeController` is coupled to the other for | Couple `GridRuntimeController` to `controller_profile.py`'s existing (module-private) `_normalize()`; match via VID/PID only | A shared standalone helper avoids an unnecessary dependency between two otherwise-independent classes; `"grid"` matches both the real bare name and the originally-assumed fuller one |

Covered end-to-end by `tests/test_grid_app_coordinator.py` and `tests/test_mapping_widgets.py`, plus a manual full-`DragonMidiWindow` smoke test against a fake transport (`pyserial` itself remains unexercised by the automated suite, per `grid_transport.py`'s own docstring) — see the completion report for the full account.
21. **First real-hardware validation pass completed (2026-11-04) against 2×PBF4 + 1×VSN1 — see the completion report for the full account.** Two genuine implementation bugs were found and fixed, neither a design error: (a) the wire-byte frame layout §2 now describes was simply wrong end to end (corrected against Intech's own `grid-protocol.ts` source plus a real captured trace, now a frozen regression fixture); (b) the MIDI port match substring would never have matched any real device (`"intechgridmidi"` can't be a substring of the real, shorter `"grid"`) — corrected in §1 and §8. One genuine design gap was found and closed: VSN1's endless encoder has its own push-button sharing the encoder's raw index, not previously modeled (§4, §7). Every other design decision in this LLD — settle semantics, address-formula correctness (confirmed exactly against 37 real address-table entries across all three modules), fail-closed collision/multi-VSN1/multi-row policies, the `ActiveController` Protocol shape, button press/release-as-velocity-0 semantics, the full `app.py` integration end to end (dropdown → settle → active → real device-name `"Grid"` connected → Mapping View rebuilt → clean teardown/reinit on profile switch) — was exercised against real hardware and held with zero design changes required.
22. **PBF4's potentiometer/button given a default behavior (Phase 1.2): bank-derived, like Korg's Knob/Mute** — resolves the PBF4 half of former Deferred item 3 below; see Module Definitions (end) and `docs/llds/static-mapping.md § Bank Derivation`/`§ Independent Rotary/Button Action Assignment`. VSN1's buttons/jog remain unwired — the other half of that item stays deferred.
23. **The single-recognized-VSN1 restriction is lifted (Phase 1.3).** A topology may now contain any number of recognized VSN1 modules; `GridControllerBuildOutcome.UnsupportedTopology` is no longer produced for VSN1 count, only for a multi-row topology (`GRID-TOPO-010`). VSN1's buttons now number globally left-to-right across every recognized VSN1 module (the same scheme PBF4's faders/pots/buttons already used), and VSN1's jog/jog-button gain a VSN1-instance ordinal in place of the old singular `None` — see Module Definitions, Active Grid Controller, Decisions & Alternatives. Driven by `docs/roadmap.md`'s Phase 1.3 task, which explicitly requires supporting repeated PBF4 *and* VSN1 modules; `docs/llds/named-controller.md`'s shape-based matching (added the same phase) depends on this LLD's new `module_shape`/`control_module` fields, also introduced here.
24. **VSN1's "8 primary buttons; verify any additional controls" roadmap line is settled from the existing implementation (Phase 1.5).** `VSN1_DEFINITION` (`grid_modules.py`) already declares 12 button-role elements (indices 0-7 plus 9-12), independently reimplemented from Intech Studio's own `grid-protocol` element table (§ Module Definitions header) — not 8. Confirmed by code audit and a new regression test (`tests/test_controller_hardware_inventory.py::test_vsn1_has_twelve_buttons_not_just_eight`), consistent with the existing `test_vsn1_button_count_is_12`/`test_vsn1_only_has_buttons_and_jog_groups_no_channels` coverage. This settles the implementation's own modeling, not real-hardware button-by-button confirmation — `docs/roadmap.md`'s "Confirm VSN1 eight-button mapping... on real hardware" line stays unchecked for that reason.
25. **"Reselect to apply" becomes a one-time, in-app prompt rather than a silent requirement the user has to remember (Phase 1.5.2).** The underlying Topology Change Policy (§10 above) is unchanged - a structural change still marks the controller `STALE` and stops Grid MIDI resolution the same tick (`GRID-TOPO-012`/`GRID-MIDI-005`). What changed is *telling the user*: the instant that happens, `app.py` shows a blocking "Intech Grid modules changed. Refresh now?" dialog (`_prompt_grid_topology_changed()`, `GRID-APP-006`) instead of relying on the user to notice the status-line text and remember to revisit the Controller Profile dropdown. OK runs `_refresh_grid_connection()` (a new shared helper factored out of the dropdown's own "Intech Grid" selection handler - both need the identical discovery-reset, and a dropdown reselect of an *already-selected* entry doesn't reliably refire Qt's `currentIndexChanged`, so the dialog needed its own direct call rather than simulating a dropdown click); Cancel leaves the controller `STALE`, identical to every tick before this feature existed. Shown at most once per STALE episode (a flag reset only by a successful refresh) so it can't be spammed by a topology that stays unsettled. **Scope explicitly narrowed during design discussion**: distinguishing "module added" (auto-adopt) from "module removed" (confirm) was considered and rejected for this phase - PBF4's positional channel numbering means a mid-chain insertion silently renumbers already-configured channels, a correctness risk serious enough (motion-control software) to defer rather than rush; the shipped version treats every structural change identically, matching §10's own table, and only changes the recovery affordance.

### Deferred — need a decision before Phase 2 implementation
1. **`GridRuntimeController`'s `setup_hint`** (if any) — e.g. "connect PBF4/VSN1 modules in a single horizontal row." Easy to add (`_install_active_controller()` already handles its absence via `getattr(controller, "setup_hint", None)`), not yet decided whether it's warranted for Phase 1's audience.
2. **Exact topology settle-window duration** (`GRID_TOPOLOGY_SETTLE_SECONDS = 0.5`) — real hardware settled in 0.74-1.66s end to end (settle window plus discovery/connect overhead) across repeated trials (2026-11-04), consistent with the proposed value; not yet stress-tested against heartbeat jitter under adverse conditions (a marginal USB cable, a very long chain), so the constant itself is not yet considered fully validated, only not contradicted.
3. **Whether/when VSN1 buttons/jog get a default behavior** — explicitly deferred past Phase 1.2; this LLD only guarantees they have a stable logical *identity* now, not a *behavior*. PBF4's pot/button are resolved (Phase 1.2, item 22 above): bank-derived into `knob_to_fader`/`mute_to_fader`, not a new `opinionated_map` entry.
4. **A future explicit multiple-Grid-chain selection UX** — out of scope for Phase 1 beyond surfacing the ambiguous state.
5. **Whether the legacy SAMD51 (`d51n20a`) firmware build's different, device-level product string (`"Intech Studio: Grid"`, no separate per-interface strings) could still appear on some currently-shipped hardware running older firmware.** The current shared descriptor source (`common/src/c/grid_usb.c`) is what this LLD designs against, consistent with the same source tree the HWCFG/element tables were confirmed against; noted for awareness, not designed around. (Moot for the MIDI/CDC match substrings specifically, now `"grid"` — a substring of either product string.)
6. **Three hardware-validation steps not yet exercised (2026-11-04 pass stopped here by explicit user choice, not a blocker found):** USB-root rearrangement (replugging the chain from a different module while keeping physical left-to-right order - §3's core normalization claim, exercised only via simulated topologies so far, not a real replug), a real Grid page change (whether `GRID-TOPO-006`'s "page change is a structural change" and the resulting `STALE` transition hold against a real page switch), and a real module disconnect/reconnect while a controller is active (whether the real disconnect timeout and `STALE` transition behave as designed). None of these exercise new code paths beyond what simulated-topology tests and the rest of this validation pass already covered at the unit level; they remain open purely for a future real-hardware confirmation pass.
