# Application Shell, Signal Monitor & Status UI

## Context and Design Philosophy

This is the glue-and-presentation layer: it starts the MIDI Input Adapter and OSC Transport, bridges their background-thread activity into Qt's main thread, tracks recency-based liveness for both channels, and renders the two-indicator status window described in the HLD. It deliberately owns nothing about MIDI/OSC protocol details or mapping semantics — those are `midi-input.md`, `osc-io.md`, and `static-mapping.md`'s territory.

**Module split:** to keep this layer testable without a running Qt application, its logic is split into plain-Python modules with no Qt dependency, plus a thin Qt shell that wires them to real widgets/timers:

- `dragonmidi/signal_monitor.py` — the Signal Monitor (below).
- `dragonmidi/status_presenter.py` — pure functions computing each indicator's display state (dot + label) from Signal Monitor reads and connection status; this is where the "single read per tick" and "dot/label independence" invariants live as testable code, not just prose.
- `dragonmidi/config.py` — the editable host/port fields' pending-vs-applied state and Apply/validation logic.
- `dragonmidi/queue_drain.py` — the generic full-drain-per-tick queue helper.
- `dragonmidi/shutdown.py` — the per-step-isolated, timeout-bounded shutdown sequence runner.
- `dragonmidi/mapping_view_model.py` — pure functions computing the Mapping View's table rows, axis-picker candidates, and min/max field validation from `MappingEngine` and `AxisDiscovery` state (below). As of Phase 6, also computes the per-Group axis-picker candidates for each fader row's 5 pickers and the Group indicator row's lit state (`docs/llds/static-mapping.md § Group Switching`).
- `dragonmidi/status_widgets.py` — the `IndicatorRow` Qt widget (dot + label), the only Qt piece of the Signal Monitor's presentation.
- `dragonmidi/mapping_widgets.py` — the Mapping View's Qt widgets (`MappingView`, `_AxisTargetEditor`), wiring `mapping_view_model.py`'s pure functions to real combo boxes/table cells. As of Phase 8, these widgets plus `ConfigurationDialog` collectively form **Table View** (below) — unchanged in content, reached by a toggle instead of being the only screen.
- `dragonmidi/control_descriptor.py` (Phase 8) — pure Python, no Qt: `ControlDescriptor` and `build_control_descriptors()` (below), a pure transformation of `mapping_view_model.py`'s existing `build_fader_rows()`/`build_configuration_rows()` output into one ordered per-control list for the Controller View's control list and Inspector. Deliberately does *not* read `control_names` directly — `control_names` omits the jog wheel and Solo entirely (neither is a `ControlsConfig`-declared transport/fader/knob/mute key), so building from the two existing row-builder outputs instead of `control_names` is what makes the control list actually complete.
- `dragonmidi/inspector_registry.py` (Phase 8) — pure Python: which `control_type` values have a registered Inspector editor (today, only `"fader"`). The actual editor widgets stay in `controller_view_widgets.py`, below; this module is the small, Qt-free piece of the dispatch that unit tests can exercise without a running application.
- `dragonmidi/controller_view_widgets.py` (Phase 8) — the Controller View body's Qt widgets: `ControllerView` (the default page of the body `QStackedWidget`, below — not the window's central widget; see Main Window Shell), its control list, and the Inspector panel that embeds `_SingleAxisTargetField` (new, extracted from `mapping_widgets.py`'s `_AxisTargetEditor`) for a selected fader, or a read-only summary label for every other control type. Also defines `_GroupSelectorRow`, the shared header's A–E button row, even though the header itself is composed in `app.py` (below) alongside the indicator/dropdown widgets it sits next to.
- `dragonmidi/app.py` — the thin Qt shell: `DragonMidiWindow` and `run()`. Constructs the real widgets, timers, and MIDI/OSC background threads, and wires them to the modules above. As of Phase 8, also composes the shared header and footer (indicators, Controller Profile dropdown, `_GroupSelectorRow`, the ⚙ Settings-dialog button, and the single Controller View/Table View toggle button) and the body `QStackedWidget` holding `ControllerView` and Table View's page — see Main Window Shell, above. This and the widget modules above are the only modules that require a Qt application to exercise; none of them carry independent logic beyond wiring.

## Signal Monitor

- Tracks one "last activity" timestamp per channel: `midi` (updated by any raw MIDI message, per `midi-input.md`'s liveness-before-normalization rule) and `dragonframe` (updated by any datagram reaching the OSC Listener, per `osc-io.md`).
- Each channel's `last_activity` is initialized to `None` ("never seen") at startup, distinct from any real timestamp — a channel with `last_activity is None` is always reported not-live, avoiding any false-positive "live" flash before the first real event arrives.
- Timestamps use a **monotonic clock** (`time.monotonic()`), not wall-clock time, so system sleep/wake or NTP corrections can never produce a negative or artificially huge elapsed time.
- A channel is considered **live** if `last_activity is not None and (now - last_activity) < LIVENESS_WINDOW` (strict less-than — the boundary itself counts as no-longer-live). Proposed default: `LIVENESS_WINDOW = 2.0` seconds — long enough that normal pauses between control moves don't flicker the indicator, short enough that "the controller was unplugged" or "Dragonframe was closed" shows up within a couple seconds.
- Both channels share the same window rather than independently-tuned windows, since the two failure modes (controller unplugged, Dragonframe closed) have similar detection-latency needs and a single constant is simpler to reason about.
- Each channel additionally carries an **error flag**, independent of the liveness timestamp: set for MIDI on a Native Mode handshake failure (`midi-input.md`), and for Dragonframe on a listener bind failure (`osc-io.md`). Combined with liveness, a channel's displayed state is one of three: **live** (recent activity), **error** (a real failure condition, regardless of activity), **quiet** (neither) — error takes precedence over quiet when both could apply. See Status UI below.
- This is the only place liveness and error-state are computed; MIDI-IN and OSC-IO only report raw timestamps and raw error flags.

## Threading and the Qt Bridge

- MIDI events arrive on `mido`'s callback thread; the OSC Listener runs its receive loop on its own thread. Neither may touch Qt widgets directly.
- Both push into thread-safe `queue.Queue` instances. A `QTimer` on the Qt main thread (proposed: 15–50ms interval, matching the prototype's proven polling cadence) drains each queue **completely** on every tick — no per-tick cap — updates the Signal Monitor's timestamps, and feeds normalized MIDI events into the Static Mapping Engine → OSC Client path. A single controller's traffic plus Dragonframe's own OSC output is far below any volume that would stall a 15–50ms tick; a cap is only worth adding if real-world testing shows otherwise.
- Each timer tick reads the Signal Monitor's state for both channels exactly once, and renders both the indicator dot and its label text from that single read — by construction, the dot and its label can never disagree about which tick's state they reflect.
- This queue-plus-poll pattern is reused deliberately from the prototype: it is a correct, already-proven way to avoid cross-thread Qt calls, independent of the prototype's tkinter-specific implementation.

## Status UI

**As of Phase 8, this mockup's layout is no longer the default screen** — the Controller View (below) is. Every mechanism described in this section is otherwise unchanged: the indicator 3-state model, Apply-gated host/port editing, the Controller Profile dropdown's discovery/default/immediate-apply behavior, the per-profile `setup_hint`, and the config load-failure count. The Controller View's header shows the two indicator dots and the Controller Profile dropdown directly; host/port editing, the `setup_hint` line, and the config load-failure line move into a new **Settings dialog**, opened by a ⚙ button in the Controller View's header (§ Settings Dialog, below) — a thin new `QDialog` wrapping these same fields and the same `ConfigController` validation/Apply logic described in this section verbatim, not a new mechanism. This is a different dialog from `ConfigurationDialog` (below), which holds per-control mapping summaries and moves into Table View instead — the two were easy to conflate by name during drafting precisely because both are "a dialog opened from a button," so this LLD calls them Settings dialog and Configuration dialog throughout to keep them distinct.

**Field widths are bounded, not stretched by the layout (2026-07-23, user's explicit choice).** `[127.0.0.1]` and each port field are given a fixed maximum width sized to their maximum realistic content — an IPv4 address/short hostname for the host field, a 5-digit port number (`65535`) for the two port fields — rather than the layout's default of letting a `QLineEdit` expand to fill whatever horizontal space its row is given. Before this change, these three fields visibly stretched across most of the window's width for no reason; the fix is purely cosmetic (`setMaximumWidth`, no change to `ConfigController`'s validation or apply behavior, `docs/specs/app-ui.md`'s `UI-CONFIG-001`).

- **Controller Profile dropdown**, above the indicator rows: populated at startup from whichever profiles the Controller Profile Loader discovered (`docs/llds/midi-input.md § Controller Profile Loading`) — today that's two, "nanoKONTROL Studio" and "nanoKONTROL2," but the dropdown itself has no fixed count or hardcoded option list; it renders whatever list it's given. Defaults to the first bundled profile (nanoKONTROL Studio) on launch, preserving the existing zero-config experience for anyone who never touches it. Changing the selection applies immediately (no Apply step, unlike the host/port fields below) — it disconnects the currently-connected device (if any), resets the Mapping Engine to the newly-selected profile's opinionated default map, and starts polling for the new profile's name match. This is a heavier action than the host/port fields' Apply, so it's a plain dropdown rather than needing a confirm step: switching controllers is inherently a "start over with a different device" action, and there is no partially-applied state to protect against the way there is with in-progress host/port text.
- **Setup hint is per-profile, sourced from config, not hardcoded to one controller.** When the selected profile has a non-empty `setup_hint` (`docs/llds/midi-input.md § Controller Profiles`), a short helper line appears beneath the dropdown showing that text verbatim — today, only the bundled nanoKONTROL2 profile sets one ("Hold SET MARKER + CYCLE while powering on for CC mode"), a direct pointer to a one-time physical setup step DragonMIDI cannot detect or perform itself. A profile with no `setup_hint` (the Studio) shows no line at all. This generalizes what was previously a hardcoded `NANOKONTROL2_SETUP_HINT` constant in `app.py` shown only for a name equality check against "nanoKONTROL2" specifically — a check that would silently do nothing for any newly-added profile needing its own hint.
- **Config load-failure indicator, independent of the setup hint.** When the Controller Profile Loader (`docs/llds/midi-input.md § Controller Profile Loading`) reports one or more config files that failed to load, a second short line appears near the dropdown — count-only, e.g. "2 controller config files failed to load" — regardless of which profile is currently selected. Absent when the failure count is zero. This is deliberately not a log viewer or a list of per-file error messages (the HLD's "no log pane" Non-Goal stays intact): it tells a novice contributor *that* something didn't load, so they know to look further, without DragonMIDI growing a detail UI for it. It can appear at the same time as a `setup_hint` line, since the two are unrelated questions.
- **Configuration button, directly beneath the Controller Profile dropdown (2026-07-23, user's explicit choice).** Opens the Configuration Dialog (below) as a modal window — clicking it calls the dialog's `.exec()`, blocking interaction with the main window until the dialog is closed, but not blocking the `QTimer` drain/refresh cycle (`Threading and the Qt Bridge` above), which keeps running during a modal `exec()`'s nested Qt event loop the same as it does otherwise. The dialog instance is created once, alongside the Mapping View, and reused on every click rather than rebuilt from scratch each time.
- Two indicator rows, each a **3-state** colored dot plus a short label: **green/lit** = live (recent activity), **amber/red** = error (Native Mode handshake failed for MIDI — Studio profile only, since the nanoKONTROL2 has no handshake to fail; listener bind failed for Dragonframe), **dim/gray** = quiet (neither — normal "waiting" state, not a failure). Error takes visual precedence over quiet.
- The MIDI row's secondary text names the connected device once found; before discovery it reads something like "Waiting for nanoKONTROL Studio…" or "Waiting for nanoKONTROL2…", matching whichever profile is currently selected. This text is driven by the MIDI Input Adapter's connection status (`midi-input.md`), **not** by the indicator dot's live/error/quiet state — the two are independent axes. **This means the dot and the label can validly disagree**: a physically connected nanoKONTROL Studio whose Native Mode handshake just failed shows the device's name *and* an amber error dot simultaneously. That combination is intended — it tells the user "your controller is plugged in, but something's wrong with it" — not a bug to be reconciled into one state. For the nanoKONTROL2 profile, the error dot never lights regardless of what the physical device is doing (no handshake exists to fail), so the dot/label pair is simpler there: live, or quiet with a name once found.
- The Dragonframe row's secondary text shows the local listen port; the "Sending to" fields show the configured Dragonframe host:port.
- Host, Dragonframe port, and listen port are lightly editable (small text fields) behind an explicit **Apply** action — edits do not take effect, and no rebind happens, until Apply is pressed. This matches the prototype's existing Apply-button pattern and avoids rebinding on invalid or partial in-progress text. Applying a Dragonframe port equal to the listen port is rejected per `osc-io.md`'s config-apply validation. Applying a changed local listen port triggers the OSC Listener to close its existing socket and rebind to the new port (`osc-io.md`'s rebind-on-config-change rule) — without this, editing the field would silently do nothing.
- These fields are machine-specific network configuration, distinct from the opinionated control mapping, which has its own surface below.
- No log pane, no menu bar (explicit non-goals carried from the HLD).

## Main Window Shell: Header, Body Stack, Footer (Phase 8)

**The main window's chrome splits into three stacked regions, only the middle one of which differs between Controller View and Table View.** This is a correction from an earlier draft of this LLD, which described Controller View as if it owned its own full-window header/footer separate from Table View's — that would either duplicate the Controller Profile dropdown/indicators in both places or leave Table View with no way to switch profiles while visible. Instead:

```
+----------------------------------------------------------------+
| DragonMIDI          ● Connected   ● Waiting for Dragonframe  ⚙ |   <- Header (shared)
|------------------------------------------------------------------|
| Controller: [ nanoKONTROL Studio ▾ ]         [A][B][C][D][E]    |   <- Header (shared)
|------------------------+-----------------------------------------|
| CONTROLS               | CONTROL SETTINGS                       |   <- Body (swaps)
| Fader 1   PAN · Axis    | Fader 1                                 |
| ...                     | [ PAN ▾ ]  [ 0 ] – [ 100 ]              |
|------------------------+-----------------------------------------|
| Dragonframe: Connected                           [Table View]    |   <- Footer (shared)
+----------------------------------------------------------------+
```

- **Header (shared by both pages, outside the `QStackedWidget`)**: application name; the two existing 3-state indicators, each a dot **plus its existing short status text** (`status_presenter.py`'s existing computed string — "Connected" / "Waiting for nanoKONTROL Studio…" / an error message — reused verbatim, not dropped; this corrects an earlier draft of this section that proposed bare dots with no label, which would have silently removed the only glanceable place a user sees *which* device is being waited for without opening a dialog); a ⚙ button opening the Settings dialog (below); the Controller Profile dropdown (`build_controller_choices()`, unchanged); and the Group selector (a horizontal row of 5 buttons using the `_GROUP_LETTERS = "ABCDE"` constant, moved from `mapping_widgets.py` to `mapping_view_model.py` so both this widget and `_GroupHeaderRow`/`_GroupIndicatorRow` import it from one place — a pure-data move, not a behavior change). Clicking a letter calls the same active-Group setter Track ◄/► already calls. Being shared, this header renders identically and stays interactive regardless of which body page is showing — switching Controller Profile or Group while Table View is visible immediately affects Table View's own rows, exactly as it does today.
- **Body (`QStackedWidget`, two pages)**: page 0 is the Controller View body (control list + Inspector, below); page 1 is Table View's body (the existing embedded fader/Group-axis grid, with a button opening the existing modal Configuration Dialog — that dialog remains a separate top-level `QDialog`, not a child of the stacked page; the page only hosts the button that opens it, same relationship the old main window already had to it).
- **Footer (shared)**: the existing "Dragonframe: Connected" text, and a single toggle button reading **"Table View"** when the Controller View body is showing or **"Controller View"** when Table View's body is showing — one button, one shared footer, not two independent ones per page.

## Controller View body (Phase 8)

- **Control hierarchy** (left column, Phase 1.1 — superseding the flat list this bullet originally described; see Control Grouping, Control Tree, and Control Search, below, for the full design): an expandable tree, one top-level item per `ControlGroup` and one child leaf per `ControlDescriptor` within it, built from the same `build_control_descriptors(build_fader_rows(engine), build_configuration_rows(engine), engine.profile)` (`control_descriptor.py`, below) grouped by `control_grouping.build_control_groups()`. Each leaf shows the descriptor's label and the same one-line assignment-summary logic this bullet always described (fader → active-Group axis state; Knob/Mute → the shared bank-derivation rule text; Solo → its real, bank-specific `select-AX{N}` value; everything else → its matching `RowView.target`, or `"Unassigned"` if none exists). Selecting a leaf highlights it and populates the Inspector; selecting (clicking) a group header only expands/collapses it. **A controller with zero faders (VSN1) simply produces no `"fader"`-type leaf and no `"Channel N"` group** — `build_fader_rows()` already returns an empty list for a zero-bank-count profile, and neither `build_control_descriptors()` nor `build_control_groups()` places a special case on an empty input list. **A VSN1-only chain still produces a non-empty hierarchy** (Buttons/Jog Wheel groups) — caught in Phase 5 testing against a real `GridRuntimeController`, not a Korg profile: an earlier two-source version of `build_control_descriptors()` silently produced an *empty* list for VSN1, since none of its controls have an `opinionated_map` entry yet.
- **No row selected (first launch, after a Controller Profile switch, or right after toggling back from Table View)**: the Inspector shows a neutral placeholder ("Select a control to edit its settings.") and no control list row is highlighted. This is a real, named state, not an unspecified default — `ControllerView` tracks "no selection" explicitly rather than defaulting to row 0, since silently auto-selecting a control could look like the user picked it.
- **Inspector** (right column): a container whose content is replaced, not just updated, each time the selected row changes. Dispatch is by the selected descriptor's `control_type`, through `inspector_registry.py`'s `has_editor(control_type)` (below): if true (today, only `"fader"`), shows one axis-picker combo and two min/max fields for the **active Group only** — not the 5-Group grid `_AxisTargetEditor` renders in Table View, since the Group selector already sits in the shared header; showing all 5 Groups redundantly here would duplicate that selector and contradict the single-control, single-setting Inspector the task's own mockup calls for. `_AxisTargetEditor`'s existing per-Group combo+min+max unit is extracted into its own small widget, `_SingleAxisTargetField` (`mapping_widgets.py`), so `_AxisTargetEditor` composes 5 of them (Table View, unchanged behavior) and the Inspector embeds exactly 1, bound to the selected fader's `key` and the currently-active Group — both call the same existing `MappingEngine.set_axis_target`/`clear_group_axis_target` methods the extracted unit already called internally. Switching the active Group (shared header selector) while a fader is selected re-binds the Inspector's one field to the new Group's target, matching "switching layers must show the appropriate existing assignments." If `has_editor` is false, the Inspector shows a short read-only label ("No settings available for this control yet.") plus the same summary text already shown in the control list — not a disabled-looking form, since there is no form to disable.
- **Controller Profile switch rebuilds the control list and clears the selection** the same way `MappingView.rebuild()`/`ConfigurationDialog`'s row rebuild already do on a profile change (`docs/llds/intech-grid.md § 14. Application Integration`) — `ControllerView` calls `build_control_descriptors()` again and resets to the "no selection" state above, rather than leaving a stale list or a dangling Inspector bound to a key the new controller doesn't have.
- **A Grid controller going `STALE` mid-session (topology rearranged while connected) is not specially handled by Controller View, matching the existing, already-accepted limitation for Table View** (`docs/llds/intech-grid.md § 10`, and Open Questions item 18 above): the control list and Inspector keep showing whatever was built from the topology at selection time; reselecting Intech Grid from the Controller Profile dropdown is still the only supported recovery, exactly as it is for Table View today. Phase 8 does not change this limitation in either direction.
- **Narrow-window behavior**: the control list has a minimum width sized to its longest existing label plus assignment summary (so e.g. `"Previous Marker   Jog All (backward)"` doesn't truncate mid-word); the Inspector has a minimum width sized to its widest control (the axis-picker combo). Below the combined minimum, the window itself has a minimum size (matching the existing app's precedent of not supporting arbitrarily small windows); above it, the two columns use a fixed left-column width with the Inspector column absorbing any extra horizontal space, rather than a 50/50 split that would waste space on a wide window with short control names.

### Settings Dialog (Phase 8)

A new, thin modal `QDialog`, opened by the ⚙ button in the shared header. Holds exactly the fields the Status UI section above already describes — host, Dragonframe port, listen port, their Apply button and validation, the per-profile `setup_hint` line, and the config-load-failure count line — moved out of what used to be the main window's permanently-visible body, into a dialog opened on demand. No new validation, persistence, or Apply logic: `ConfigController`'s existing pending/applied/Apply-validate behavior (`dragonmidi/config.py`) is reused unchanged; this dialog is a new container, not a new mechanism. Distinct from `ConfigurationDialog` below — that dialog holds per-control mapping summaries (mapping data); this one holds machine-specific network configuration, matching the HLD's existing distinction between the two kinds of fields.

## Control Grouping, Control Tree, and Control Search (Phase 1.1)

A follow-up to Phase 8's flat Controller View control list, which a direct user request ("I don't want the long list of channels and buttons on the left") and a formal Phase 1.1 task together replaced with an expandable, hardware-aware hierarchy. Two new pure, Qt-free pieces and one widget rewrite — no change to `MappingEngine`, the Preset Store, or Table View.

**`control_grouping.py` — `ControlGroup` and `build_control_groups()`.**

```python
    id: str
    label: str
    controls: tuple[ControlDescriptor, ...]
    kind: str  # "channel" | "global" | "fallback" | "vsn1_buttons" | "vsn1_jog"

def build_control_groups(descriptors, active_controller) -> list[ControlGroup]:
    ...  # see module for the full ~60-line implementation
```

- **A control's Bank membership is derived entirely from data `ActiveController` already exposes — never from the controller's name, and never from parsing a display-name string.** A Fader is a member of its own Bank (`bank_fader_keys.index(key)`); Knob/Mute resolve via `bank_fader_key()`, a method every `ActiveController` already implements (`GridRuntimeController.bank_fader_key` literally is `knob_to_fader.get(key) or mute_to_fader.get(key)`); Solo resolves via its position in `websocket_keys.solos` — the exact tuple `MappingEngine.process_websocket`'s own `N + bank_count·(g-1)` formula already indexes into. No new reverse-lookup map was needed for any of these three.
- **PBF4's Pot/Button join their Fader's Bank by matching numeric index within a small, explicitly recognized set of Grid key tags (`"grid_pbf4_pot"`, `"grid_pbf4_button"`) — the one place this module needs controller-family-specific knowledge, not a zero-knowledge universal rule.** `grid_controller.py`'s per-tag counters (`grid_fader`, `grid_pbf4_pot`, `grid_pbf4_button`) each increment once per element within one module's pot→fader→button element-index pass (PBF4's elements are laid out 0-3 potentiometer, 4-7 fader, 8-11 button), so Pot *N*, Fader *N*, and Button *N* (same *N*) are always the same physical channel strip — true for a single module, and still true across a multi-module chain (each module contributes its own pot/fader/button triad to the same three counters in one coherent pass; an interposed VSN1 module touches none of these three counters, so it can't desynchronize them). Verified directly: a `PBF4, VSN1, PBF4` chain's second module's Channels 5-8 still pair the right Fader/Pot/Button together (`test_pbf4_vsn1_pbf4_chain_channel_numbering_ignores_the_interposed_vsn1`).
- **VSN1's controls never resolve to a channel at all — by construction, not by a VSN1-specific exclusion rule.** `_bank_index_for()` only recognizes `grid_pbf4_pot`/`grid_pbf4_button` as Grid's channel-aligned tags; VSN1's own tags (`grid_vsn1_button`, `grid_vsn1_jog`, `grid_vsn1_jog_button`) are never checked against `bank_count`, so they always fall through to the leftover bucket, which a second check then routes to `"Buttons"`/`"Jog Wheel"` instead of `"Transport & Global"`.
- **Group order is Channel 1..N (only for Banks with at least one actual member), then any VSN1-specific groups, then one terminal catch-all** — `"Transport & Global"` when at least one channel/VSN1 group exists (so the leftovers are genuinely transport-and-global controls: Play, Stop, Scene, Cycle, Markers, Track, the Korg jog wheel's two rows), or `"Controls"` when none does (a controller with no recognized structure at all, `UI-CTRLGROUP-004`'s fallback — "no physical control should disappear merely because grouping information is missing").
- **Every descriptor lands in exactly one group — verified directly** (`test_every_descriptor_appears_in_exactly_one_group`, `test_vsn1_only_every_control_still_represented`), not merely assumed from the control-flow reading correctly.

**`controller_view_widgets.py`'s control list becomes a `QTreeWidget` (`_ControlTreeWidget`, a one-method subclass — see below), not a `QListWidget`.**

- **Group header items carry no `ItemIsSelectable` flag.** This is what lets a group header be clicked (to expand/collapse) without ever becoming Qt's `currentItem()` — which is what lets a previously-selected leaf's highlight survive a header click elsewhere (`UI-CTRLTREE-003`), without any manual "remember and restore the selection" bookkeeping. `_on_item_clicked` (connected to `itemClicked`) explicitly toggles `setExpanded()` for a clicked group header — Qt's own default click-to-expand behavior only responds to the disclosure triangle, not a click anywhere on the row, and the task's spec wants the latter.
- **Selection/Inspector updates are wired to `currentItemChanged`, filtered by an explicit per-item `"group"` vs `"control"` tag (`Qt.ItemDataRole.UserRole`) — not by `item.parent() is None` alone.** The synthetic "no matches" empty-state item (below) is also a top-level item with no parent, but isn't a group either; tagging every item's *kind* explicitly, rather than inferring it from tree position, keeps the one dispatch check correct for all three item kinds without a growing set of structural special cases.
- **`_ControlTreeWidget.focusInEvent` clears `currentItem()` back to none if Qt's own focus handling left it on a non-`"control"` item.** Removing `ItemIsSelectable` from group headers turned out to prevent the Phase 8 `QListWidget` bug (silently promoting `currentRow()` −1 → 0 on first real keyboard focus) in the common case — Qt has no selectable candidate at index (0, 0) to promote to — but a direct `focusInEvent` call (exercised only by this class's own unit test, not by any headless construction-only test) showed Qt's base class can still set `currentItem()` to that same non-selectable item via "current" tracking, which is a distinct concept from "selected." Harmless functionally (the kind-tag check in `_on_current_item_changed` already ignores it), but left uncorrected it would leave a lingering focus rectangle on a group header the user never touched — corrected the same session the test that caught it was written, not by running the real app.
- **Rebuilding (`_rebuild_rows()`, a Controller Profile switch) tears down and recreates every item; `refresh()` (every UI tick) only ever calls `item.setText()` on existing leaves.** Expand/collapse state is therefore preserved for free across every tick (nothing touches it) and intentionally reset on a profile switch (a fresh tree has every group collapsed by default) — matching the task's "remember expanded groups while navigating within the same controller" (not across a controller change, where a totally different set of groups exists anyway).

**Search**: a `QLineEdit` above the tree, filtering by substring match (case-insensitive) against each leaf's already-rendered text (label + live summary — the same text `refresh()` already computed, not a new recomputation path) and its group's label.

- **A group is visible if its own label matches, or at least one child's rendered text matches; a visible group is always shown expanded, regardless of its prior state.** A child's visibility follows the same per-child check, independent of its siblings — so `"fader"` reveals every channel (each has exactly one Fader-labeled child) without also revealing every other child in those groups.
- **Expand state is captured once, the first time a search becomes non-empty (`_expanded_group_ids_before_filter`), and restored exactly when the search is cleared back to empty — not continuously snapshotted on every keystroke**, which would capture the filtered (not the user's real) expand state after the first character.
- **Filtering never touches `_selected_key` or the Inspector, in either direction.** A selected leaf that becomes hidden by the filter stays selected; the Inspector keeps showing its settings. This was a deliberate design choice, not an oversight — re-read directly against the task's own "do not change the selected control or its mapping when filtering" requirement before considering this phase done.
- **A single, non-selectable, synthetic tree item reading "No matching controls." stands in for an empty result — not a separate overlay widget or a disabled tree.** Added as the lone top-level item when no group matches, removed the moment one does; reuses `QTreeWidgetItem`, so no new widget type was introduced just for this state.
- **Knob/Mute's rule text (e.g. "Bank-derived: follows fader's axis...") legitimately contains the word "fader."** Searching `"fader"` therefore surfaces both the actual Fader row and every channel's Knob row — confirmed as correct, matched-on-full-rendered-text behavior (`UI-CTRLSEARCH-001`'s own wording: "a leaf's own rendered text," not "a leaf's label"), not a bug, when a test's narrower assumption first disagreed.

The engine keeps sending to that name regardless (`MAP-AXIS-006`); the picker's job is to restrict *new* selections, not to babysit existing ones.

Min/max accept any real values including `min > max` or `min == max` (`MAP-AXIS-002`) — no field-level validation beyond "is a number." Text that fails to parse as a number is not applied — that picker's last successfully-applied target (if any) is left in effect, with no error dialog.

A cleared picker shows the same "Discovering…"/"No axes found"/empty-selection states as a fresh row's picker always has.
- **Rescan axes** calls `OscListener.rescan()` directly; it does not reset any row's already-configured target, in any Group, only what the pickers offer going forward.
- **The (Bank, Group) axis-assignment table persists across launches** — loaded/saved via the Preset Store (`docs/llds/static-mapping.md § Preset Store`). The active Group itself resets to Group 1 on every launch, unpersisted (`docs/llds/static-mapping.md § Group Switching`), so the Group indicator row above always starts lit on Group 1 regardless of which Group's pickers hold saved values.

## Control Descriptor and Inspector Editor Registry (Phase 8)

Two small, Qt-free modules supporting the Controller View above, neither touching `MappingEngine`'s internal representation, `ActiveController`'s existing Protocol surface, or the Preset Store's file format.

**`control_descriptor.py` — `ControlDescriptor` and `build_control_descriptors()`.**

```python
@dataclass(frozen=True)
class ControlDescriptor:
    key: _Key
    label: str
    control_type: str  # "fader" | "button"

def build_control_descriptors(
    fader_rows: list[RowView],
    configuration_rows: list[RowView],
    active_controller: ActiveController,
) -> list[ControlDescriptor]:
    descriptors = [
        ControlDescriptor(key=row.key, label=row.name, control_type="fader")
        for row in fader_rows
    ]
    seen = {row.key for row in fader_rows}

    for knob_key in active_controller.knob_to_fader:
        label = active_controller.control_names.get(knob_key, "Knob")
        descriptors.append(ControlDescriptor(key=knob_key, label=label, control_type="button"))
        seen.add(knob_key)
    for mute_key in active_controller.mute_to_fader:
        label = active_controller.control_names.get(mute_key, "Mute")
        descriptors.append(ControlDescriptor(key=mute_key, label=label, control_type="button"))
        seen.add(mute_key)
    ws_keys = active_controller.websocket_keys
    if ws_keys is not None:
        for solo_key in ws_keys.solos:
            descriptors.append(ControlDescriptor(key=solo_key, label="Solo", control_type="button"))
            seen.add(solo_key)

    seen |= {KNOB_ROW_KEY, MUTE_ROW_KEY, SOLO_ROW_KEY}
    for row in configuration_rows:
        if row.key in seen:
            continue  # the collapsed Knob/Mute/Solo summary rows - superseded by the per-bank expansion above
        descriptors.append(ControlDescriptor(key=row.key, label=row.name, control_type="button"))
        seen.add(row.key)

    for key, label in active_controller.control_names.items():
        if key in seen:
            continue
        control_type = "fader" if key in active_controller.fader_keys else "button"
        descriptors.append(ControlDescriptor(key=key, label=label, control_type=control_type))
    return descriptors
```

- **Four sources, each catching what the others miss.** `control_names` omits the jog wheel and Solo entirely for a Korg profile (`build_control_names()`, `mapping.py` — neither is a `ControlsConfig`-declared key); `build_fader_rows()`/`build_configuration_rows()` omit VSN1's buttons/jog entirely (Grid's `GridRuntimeController` never wires them into `opinionated_map` — `docs/high-level-design.md § Delivery Phasing`'s Phase 7 note). Testing against a real `GridRuntimeController` (not just the two Korg profiles) caught the second gap: it produced an *empty* list for a VSN1-only chain. The `control_names` loop is deliberately the final *fallback* — it only contributes a key nothing earlier already did.
- **Knob, Mute, and Solo are each expanded into one descriptor per real key — Phase 1.1's reversal of Phase 8's "exclude entirely" decision.** A user request to declutter the flat Controller View list (post-Phase-8) first removed Knob/Mute/Solo outright; Phase 1.1's per-channel grouping (below) then needed them back, because **grouping by Bank requires knowing which Bank each belongs to** — information the single collapsed `KNOB_ROW_KEY`/`MUTE_ROW_KEY`/`SOLO_ROW_KEY` summary row can't carry (it's one row covering all 8 Banks at once). Collapsing into one row remains exactly correct for Table View's flat presentation (`docs/llds/app-ui.md`'s 2026-07-23 decision, unchanged); it was never the right shape for a hierarchy organized by channel. The collapsed rows themselves are excluded from `configuration_rows`'s contribution here (superseded, not duplicated).
- **`control_type` stays coarse: `"fader"` / `"button"` only.** Knob/Mute/Solo all classify `"button"` — none has a registered Inspector editor (below), so there is nothing finer to distinguish yet. See Open Questions for when a finer taxonomy becomes necessary.
- **Assignment-summary text is computed by the Controller View widget, not stored on `ControlDescriptor`.** A descriptor is a stable identity (`key`, `label`, `control_type`); its current summary changes every UI tick the same way existing rows already do, so baking a summary string into the descriptor would immediately go stale. For Knob/Mute, the widget reuses the existing `KNOB_ROW_KEY`/`MUTE_ROW_KEY` row's `target` text (the shared bank-derivation rule, not a bank-specific value — nothing bank-specific is actually known to summarize safely for these two). For Solo, the widget computes a real, bank-specific value directly (`N + bank_count·(g-1)`, the same formula `MAP-WS-002` uses) — Solo is never actually "unassigned," so falling through to a generic "Unassigned" text for it, as an earlier revision did, was a real bug, not just an imprecise summary (caught re-reading against the Phase 1.1 task's own worked example, not by a failing test). Everything else reuses the matching `RowView` from a fresh `build_configuration_rows()` call, or shows `"Unassigned"` for a fallback-group descriptor with no matching `RowView` at all.

**`inspector_registry.py` — which `control_type`s have an editor.**

```python
_TYPES_WITH_EDITOR: frozenset[str] = frozenset({"fader"})

def has_editor(control_type: str) -> bool:
    return control_type in _TYPES_WITH_EDITOR
```

- **Deliberately minimal: a membership test, not a widget factory.** The actual editor widget (today, `_SingleAxisTargetField` — see Controller View body, above) is constructed in `controller_view_widgets.py`, which is allowed to import Qt; keeping `inspector_registry.py` Qt-free means `has_editor()` is unit-testable the same way every other pure module in this LLD already is, without a `QApplication` fixture.
- **A future editor (center-stop shuttle, absolute-knob jog) registers by adding its `control_type` to `_TYPES_WITH_EDITOR` and a corresponding branch in `controller_view_widgets.py`'s dispatch** — the Controller View's control list and Inspector container do not change; only the registry's membership set and the dispatch's widget-construction branch grow. This is the "documented extension point" the HLD's Phase 8 description refers to.
- **Not a decorator-based or dict-of-factories registry**, despite "registry" in the name — a 1-entry frozenset is the honest size of today's need; a factory-dispatch mechanism is easy to introduce later (when there are 2+ real editors to dispatch between) without this phase speculatively building it for a future that doesn't exist yet in the codebase.

## Bootstrap and Shutdown

- Single entry point: start the MIDI discovery/poll loop, start the OSC Listener thread, construct the Qt application and main window, start the drain `QTimer`, enter the Qt event loop.
- On quit: release Native Mode if active, close MIDI input/output ports, stop the OSC Listener thread, close the UDP client socket — mirrors the prototype's `_on_close` cleanup sequence. Each step runs in its own try/except so one failing or hanging step (e.g. a bad port blocking Native Mode release) cannot prevent the others from running; the overall shutdown sequence is capped by a short timeout before the process force-exits.

## Decisions & Alternatives

| Decision | Chosen | Alternatives Considered | Rationale |
|---|---|---|---|
| Liveness computation location | Centralized Signal Monitor, single shared window | Per-channel independently tuned windows | Simplicity; both channels' expected quiet periods are similar enough for one constant in phase 1 |
| Thread bridge | `queue.Queue` + `QTimer` poll | Qt signals/slots emitted directly from worker threads | Reuses the prototype's already-proven pattern; avoids subtleties of emitting Qt signals from non-Qt threads |
| Settings persistence | *(open — see below)* | Persist host/ports across launches (prototype's `storage.py`) vs. always reset to defaults | Not yet decided; brushes against the "no config UI" non-goal even though it's arguably just network defaults, not mapping config |
| Indicator state model | 3-state (live / error / quiet) | 2-state (lit / dim) | A silently-failed listener bind or Native Mode handshake would otherwise look identical to ordinary "no traffic yet" — actively misleading for an app whose purpose is accurate status |
| `last_activity` initial value | `None` sentinel, distinct from any timestamp | Default to `now()` or epoch `0` | Avoids a false-positive "live" flash at boot (`now()`) and is more explicit than relying on a huge-elapsed-time side effect (`0`) |
| Clock source | `time.monotonic()` | Wall-clock `time.time()` | Immune to sleep/wake and NTP corrections by construction, fully resolving the clock-jump concern |
| Liveness boundary | Strict `<` (boundary itself is not-live) | Inclusive `<=` | Arbitrary but explicit; needed a pick, `<` was simpler to state as "not live" |
| Queue drain strategy | Full drain every tick, no cap | Bounded per-tick drain | Realistic traffic volume from one controller + Dragonframe is far below what would stall a 15–50ms tick; add a cap only if testing proves otherwise |
| Shutdown robustness | Per-step try/except + overall timeout | Single try/except around the whole sequence | One hanging/failing step (e.g. bad port during Native Mode release) must not block the rest of cleanup or hang app quit indefinitely |
| Live host/port edits | Explicit Apply action, no live-as-you-type rebind | Rebind immediately on every keystroke/change | Matches the prototype's existing pattern; avoids rebinding on invalid or partial text |
| Dot/label consistency | One Signal Monitor read per tick feeds both | Independent reads for dot and label | Guarantees by construction that the two can never show different ticks' state |

Required reversing part of item 19/the Decisions table's "Knob, Mute, and Solo are excluded entirely" choice: per-channel grouping needs to know which Bank each belongs to, so each is now expanded into one descriptor per real key instead of staying excluded — see Control Descriptor and Inspector Editor Registry, and Control Grouping/Control Tree/Control Search, above. ### Deferred
1. Should the Dragonframe host, Dragonframe port, and local listen port persist across app launches (like the prototype's JSON state file), or always reset to their defaults? A minimal persisted-settings file is small in scope but is the first piece of "state the app remembers," which is adjacent to the deferred configuration phase.
2. Phase 2's full Mapping View (Add/Edit/Duplicate/Remove, MIDI-learn, presets, arbitrary custom OSC paths) is out of scope for this section entirely — see the HLD's Phase 2 description. Knob/Mute are now bank-derived (see above), but remain non-independently-configurable; independently retargeting them is still Phase 2.
3. Exact `LIVENESS_WINDOW` value (proposed 2.0s) is a tunable constant pending real hardware testing, not a hard requirement yet.
4. Whether the Controller Profile selection should persist across app launches — same open question as host/port persistence above, not yet decided (also noted in `docs/llds/midi-input.md`).
5. Whether the engine-wide Fader mode itself should ever persist across launches (like the (Bank, Group) axis table does) is not yet decided — today it always resets to axis mode on launch, matching `MAP-AXIS-008`'s default and the general "mode doesn't persist, assignments do" pattern already established for the pre-2026-07-23 per-fader flag; revisit if real usage shows the reset-to-axis-every-launch default is inconvenient.
6. **`ControlDescriptor.control_type`'s coarse `"fader"`/`"button"` vocabulary will need to grow** once a second Inspector editor is built for a type it currently can't distinguish (e.g. a relative jog wheel vs. an ordinary button both classify as `"button"` today). That likely requires extending the `ActiveController` Protocol itself (`dragonmidi/active_controller.py`, documented in `docs/llds/intech-grid.md § Active Grid Controller`) with a generic per-control-type field both `ControllerProfile` and `GridRuntimeController` populate — a cross-segment change deliberately not made yet since nothing currently reads a finer distinction. Scope this when the Shuttle or Jog editor is actually built, not speculatively now.
7. **Whether search should also match against raw MIDI identifiers (CC numbers, note numbers)** is not currently supported — only rendered label/summary/group-label text is matched (`UI-CTRLSEARCH-001`). Revisit if users want to search by CC number directly.
8. **Whether a Bank's Knob/Mute summary text should ever become bank-specific** (e.g. "Nudges AX1" once Fader 1 is assigned AX1) rather than reusing the shared, bank-independent rule text every Bank currently shows identically, is not decided — the shared text is always correct and safe; a bank-specific version would need new derivation logic not written yet, and risks being wrong rather than merely generic if that derivation has a gap.
